# The RHO Spec Does NOT Mention a "Trajectory Comprehender LLM"

The RHO Stage Design spec (`2026-08-17-rho-stage-design.md`) does **not** include a dedicated "trajectory comprehender LLM" as a separate component. Here's what it actually specifies for trajectory processing:

## What the Spec Does Specify

### 1. Trajectory Digest (Phase 1 — History Load)
The spec mentions a **bounded trajectory digest** as part of the `HistoricalRecord`:

> *"A `HistoricalRecord` carries: `task_id`, `input_text`, a bounded trajectory digest, `tool_observations`, `final_output`, and `harness_version`."*

This is described as a **mechanical truncation** (head-and-tail, default 10,000 tokens), not an LLM comprehension step:

> *"The trajectory digest is bounded (default 10,000 tokens, head-and-tail truncation)."*

### 2. Difficulty + Fingerprint Judge (Phase 2)
This is the closest thing to a "trajectory comprehender" — it reads the trajectory digest and produces a structured summary:

> *"An ordinary structured LLM call, not an agentic one, matching the paper."*

It returns:
```json
{"difficulty": 7.8, "abstract_fingerprint": "A multi-step retrieval task where ..."}
```

But this is a **judge**, not a comprehender. It assigns difficulty and produces a fingerprint for coreset selection. It doesn't produce a rich understanding of the trajectory for downstream use.

### 3. Group Diagnosis (Phase 5)
This is the component that actually **analyzes trajectories in depth**:

> *"One call per coreset task, receiving all G trajectories together. This is a distinct stage from the per-rollout causal analyzer, which continues to run and whose findings are supplied as supporting evidence."*

The group diagnoser receives all G trajectories and produces:
```json
{
  "recurring_failure_mode": "...",
  "disagreements": ["..."],
  "self_validation_observed": false,
  "severity": 0.0,
  "improvement_direction": "...",
  "candidate_surfaces": ["instructions"]
}
```

## What's Missing: A Dedicated Trajectory Comprehender

The spec does **not** include a step that:
- Reads a raw trajectory and produces a structured natural-language summary
- Compresses a 56-event DAG into a human-readable narrative
- Extracts key decision points, tool call sequences, and failure modes
- Produces a "comprehension" that downstream components (diagnoser, optimizer) can consume

The closest existing components are:
1. **The causal analyzer** (per-rollout, produces blame graphs) — but this runs during rollouts, not as a preprocessing step
2. **The group diagnoser** (per-task, receives all G trajectories) — but this is a diagnosis step, not a comprehension step

## Should You Add One?

If you're asking whether a trajectory comprehender would be valuable, the answer depends on what problem you're trying to solve:

| Problem | Solution |
|---|---|
| The group diagnoser's prompt is too long (all G trajectories) | Add a trajectory summarizer that compresses each trajectory before the diagnoser sees them |
| The RHO optimizer needs to understand *why* a trajectory failed | The group diagnoser already produces this (`recurring_failure_mode`, `improvement_direction`) |
| You want a reusable "trajectory understanding" that multiple downstream components can consume | Add a dedicated comprehender that produces a structured summary |

The spec's current design assumes the group diagnoser can handle all G trajectories in a single prompt. If trajectories are long (56 events × G=3 rollouts = 168 events), this may exceed context limits. A trajectory comprehender/summarizer could solve this, but it's not currently in the spec.
