# How the Causal Analyzer and Editor Work in AgentEvolve

Yes, they are fundamentally **LLM calls** — but they are heavily constrained, structured, and validated LLM calls. They are not free-form chat completions. Here's exactly how each one works.

---

## I. The Causal Analyzer (The "Reflect" Step)

### What It Receives

The analyzer is invoked by the orchestrator after a rollout completes:

```python
# In SequentialGepaRunner.observe():
trace, analysis = self.analyzer_judge.analyze(task, trace)
```

The analyzer receives:
- The **task contract** (what the agent was supposed to do)
- The **execution trace** (the rich `CausalTrace` with 56 events, parent/child edges, tool calls, LLM calls, state transitions)
- The **artifact inventory** (what skills/policies/memory the agent had)

### What It Produces

The analyzer is a **single structured LLM call** that outputs a JSON verdict conforming to a strict schema. It produces a `CausalAnalysis`:

```python
@dataclass
class CausalAnalysis:
    mechanism: str           # "deprecated schema propagated to executor"
    severity: float          # 0.9
    score: float             # 0.2 (how well the task went)
    blame_graph: BlameGraph  # The causal attribution
    analyzer_model_id: str   # Which model produced this
    judge_model_id: str      # Which model judged it
```

The `BlameGraph` contains nodes:

```python
@dataclass
class BlameNode:
    actor_id: str    # "gaia-react" (from the trace)
    blame: float     # 0.75 (how much this actor caused the failure)
    artifacts: tuple[str, ...]  # ("skills/retrieval-recovery.md",)
```

### The Critical Constraint: Trace-Backed Evidence

The analyzer **cannot invent** blame nodes. The architecture mandates:

> *"A node with no trace evidence is invalid. Synthetic placeholder nodes are forbidden; absence of evidence must be expressed as `insufficient_evidence`."*

This means:
- Every `actor_id` in the blame graph must correspond to an actual actor observed in the trace (e.g., `"prepare"`, `"call_model"`, `"sandbox"` from the CUGA trace)
- Every `artifact` reference must correspond to an actual artifact the actor interacted with
- If the analyzer cannot determine causality, it must return `status="insufficient_evidence"` — not a guess

### The Conversion to CausalFinding

After the analyzer produces its output, the orchestrator converts it:

```python
def finding_from_analysis(self, analysis, *, task, candidate_id, trace_id, verdict_id, writable_artifact_ids):
    blamed = sorted(analysis.blame_graph.nodes, key=lambda n: (-n.blame, n.actor_id))
    
    if not blamed:
        # NO synthetic node. Honest "insufficient_evidence".
        return CausalFinding(
            status="insufficient_evidence",
            blame_graph=BlameGraph(nodes=()),
            ...
        )
    
    top = blamed[0]
    # Attribute the top actor's blame to the adapter's writable artifacts
    nodes = (
        BlameNode(actor_id=top.actor_id, blame=top.blame, artifacts=write_set),
    ) + tuple(
        BlameNode(actor_id=n.actor_id, blame=n.blame, artifacts=())
        for n in blamed[1:]
    )
    
    return CausalFinding(
        status="observed",
        blame_graph=BlameGraph(nodes=nodes),
        ...
    )
```

### Is It One LLM Call?

**Yes.** The architecture explicitly states:

> *"The default operational mode uses one analyzer+judge call for each selected evidence unit."*

This is a cost/coordination choice. The analyzer is a single LLM call with a structured prompt that says: "Given this trace, this task, and this artifact inventory, produce a JSON verdict with failure mechanisms, blame graph, and counterfactual evidence."

The **consensus mode** (multiple analyzer calls with different prompts) is feature-gated and not the default.

## II. The Editor (The "Mutate" Step)

### What It Receives

The editor is invoked after an issue is selected:

```python
# In SequentialGepaRunner.propose_edits():
request = EditorRequest(
    base_workspace=workspace,
    task=task,
    analysis=analysis,          # The causal finding from the analyzer
    issue_id=issue.issue_id,
    write_set=write_set,        # Artifacts the editor is ALLOWED to modify
    current_artifacts=current,  # Current content of those artifacts
    history_refs=history,       # Previous attempts for this issue (from memory RAG)
)
repair = repair_once_then_classify(self.editor, request)
```

The editor receives:
- The **issue** (what's broken, which artifact to fix)
- The **causal finding** (why it's broken, from the analyzer)
- The **current artifact content** (the text of the skill/policy/memory to edit)
- The **authorized write set** (which artifacts it can touch)
- The **edit history** (what was tried before and what worked/failed)

### What It Produces

The editor is a **single structured LLM call** that outputs an `EditPlan`:

```python
@dataclass
class EditPlan:
    attempt_id: str
    issue_fingerprint: str
    read_requests: tuple[str, ...]       # Artifacts it wants to read (NOT write)
    authorized_writes: tuple[str, ...]   # Artifacts it declares it will write
    edits: tuple[ArtifactEdit, ...]      # The actual edits
    rationale: str                        # Why it's making these edits
    risks: tuple[str, ...]               # What could go wrong
    expected_effect: ExpectedEffect      # What it expects to happen
```

Each `ArtifactEdit` is:

```python
@dataclass
class ArtifactEdit:
    artifact_id: str              # "skills/retrieval-recovery.md"
    operation: str                # "replace", "append_section", "delete"
    payload: Mapping[str, object] # {"content": "new text here..."}
```

### The Critical Constraint: Authorization

The editor **cannot write outside its authorized set**. This is enforced at two levels:

```python
# Level 1: Editor-side validation
def validate_editor_plan(plan, readable, authorized_writes):
    if not set(plan.read_requests) <= readable:
        raise WriteAuthorizationError("editor requested a non-readable artifact")
    if not set(plan.authorized_writes) <= authorized_writes:
        raise WriteAuthorizationError("editor declared an unauthorized write")
    if any(edit.artifact_id not in authorized_writes for edit in plan.edits):
        raise WriteAuthorizationError("editor edit is outside authorization")

# Level 2: Adapter-side enforcement
# The adapter independently rejects edits outside the authorized set
```

### The Repair Protocol

If the editor's response is malformed (wrong schema, invalid JSON, unauthorized writes), it gets **exactly one correction opportunity**:

```python
def repair_once_then_classify(editor, request):
    response = editor.propose_edit(request)
    
    if is_valid(response):
        return RepairResult(response=response, correction_requests=0)
    
    # ONE repair attempt
    correction = build_correction_request(response, request)
    repaired_response = editor.propose_edit(correction)
    
    if is_valid(repaired_response):
        return RepairResult(response=repaired_response, correction_requests=1)
    
    # Still malformed → record as non-promotion
    return RepairResult(response=None, correction_requests=1, status="malformed")
```

This is not a retry loop. It's one correction, then stop. The architecture explicitly forbids unlimited retries.

### Is It One LLM Call?

**Yes, with one possible correction call.** The editor is a single LLM call that produces structured edits. If the output is malformed, one additional call is made with a correction prompt. Maximum two LLM calls per edit attempt.

## IV. Summary: What's an LLM Call and What's Not

| Step | LLM Call? | What It Does |
|---|---|---|
| Rollout | ❌ No | CUGA agent executes the task |
| **Analyze** | ✅ **Yes (1 call)** | LLM reads trace → produces blame graph |
| Build Issue | ❌ No | Converts analysis to Issue (pure code) |
| Select Issue | ❌ No | DPP math (pure linear algebra) |
| **Edit** | ✅ **Yes (1-2 calls)** | LLM reads issue → produces artifact edits |
| Apply Edits | ❌ No | Modifies workspace files (pure code) |
| Validate | ❌ No | Runs rollouts on edited agent (no LLM analysis) |
| Decide | ❌ No | Acceptance logic (pure code) |

**Per GEPA attempt: 2-3 LLM calls total** (1 analyzer + 1-2 editor). The rest is deterministic code, math, and rollouts.

## V. How This Differs From GEPA

The GEPA paper uses a simpler reflect/mutate cycle:
1. Reflect: "What went wrong?" (free-form LLM analysis)
2. Mutate: "Fix it." (free-form LLM edit)

AgentEvolve adds:
1. **Causal blame attribution** (not just "what went wrong" but "which artifact caused it")
2. **Trace-backed evidence** (no synthetic blame nodes)
3. **DPP diversity selection** (not just "fix the worst thing" but "fix diverse things")
4. **Focused validation** (origin + regression probes, not just "did it work?")
5. **Protected floors** (some capabilities are sacred and cannot regress)
6. **Edit memory RAG** (the editor learns from previous attempts)
7. **Authorization boundaries** (the editor can only touch what it's told to touch)

The LLM calls are the same fundamental mechanism as GEPA, but they are embedded in a much more constrained and validated pipeline.

The architecture's Phase 5 parallel model is about **storage and coordination**, not agent execution:

| Concern | What It Means | CUGA Subagents Help? |
|---|---|---|
| Snapshot/lease mechanics | Two edits can't modify the same artifact simultaneously | ❌ No — this is a storage lock, not an agent concern |
| Atomic batch commits | Either all records publish or none do | ❌ No — this is a database transaction |

# Designing the Ideal CUGA Editor Agent

Your instinct is correct. The analyzer is the simpler replacement — it reads traces and produces blame graphs. The editor is the harder one because it must **reason about the consequences of its own edits before making them**. Let me design this properly.

---

## I. Why the Editor Is Fundamentally Harder Than the Analyzer

The analyzer is **observational**: it looks at what happened and explains it.

The editor is **interventional**: it must predict what *would* happen if it changed something. This requires:

1. Understanding the current state (what the analyzer found)
2. Learning from history (what worked/failed before)
3. Predicting consequences (what would happen if I edit X)
4. Validating predictions (would this actually improve things)

A single LLM call can do step 1. Steps 2-4 require **tools and multi-step reasoning**. This is exactly why a CUGA agent is the right architecture.

## IV. The Tag-Based Tentative State Construction (Your Key Insight)

Your idea of wrapping each editable artifact with a unique tag is the right approach. Here's how to implement it properly:

### Step 1: Tag Injection at Harness Materialization

When the wrapper materializes a harness, it injects unique tags into each artifact's content:

```python
def materialize_harness(harness_config, workspace_dir):
    for artifact_id, content in skills.items():
        tag = f"[ARTIFACT:{artifact_id}:{version_hash[:8]}]"
        tagged_content = f"{tag}\n{content}\n[/ARTIFACT:{artifact_id}]"
        # Write tagged content to workspace
        (workspace / "skills" / artifact_id).write_text(tagged_content)
```

### Step 2: Tag Recording in the Trace

When CUGA loads the harness, the tagged content appears in the agent's messages and state. The trace records which tags were loaded:

```python
# In the trace events:
{
    "event_id": "graph:4",
    "kind": "llm_call_start",
    "payload": {
        "messages_ref": "eba5adb8...",
        "loaded_artifacts": [
            "ARTIFACT:skills/retrieval-recovery:a3f7b2c1",
            "ARTIFACT:policies/execution:8d4e5f6a",
            "ARTIFACT:memory/task-context:1b2c3d4e"
        ]
    }
}
```

### Step 3: Tentative State Construction

The editor can now build a tentative state by:

1. **Finding the relevant checkpoint** in the trace where the artifact was used
2. **Extracting the agent's state** at that checkpoint
3. **Locating the tagged artifact content** in the state via regex
4. **Replacing the tagged content** with the proposed edit
5. **Simulating forward** from that modified state

```python
def build_tentative_state(
    trace_id: str,
    checkpoint_sequence: int,     # Which checkpoint to start from
    artifact_id: str,             # Which artifact to modify
    proposed_content: str,        # The new content
) -> TentativeState:
    """Construct the agent's state as if the edit were applied.
    
    1. Load the checkpoint state from the trace
    2. Find the tagged artifact content via regex:
       pattern = r'\[ARTIFACT:{artifact_id}:.*?\].*?\[/ARTIFACT:{artifact_id}\]'
    3. Replace the matched content with proposed_content
    4. Return the modified state
    """
```

### Step 4: Lightweight Counterfactual Simulation

**Critical constraint:** The editor should NOT run a full CUGA rollout for simulation. That's what `evaluation.py` does AFTER the edit is submitted. The editor's simulation is a **pre-filter** — a lightweight heuristic check.

```python
def simulate_counterfactual(
    tentative_state: TentativeState,
    task_id: str,
    simulation_mode: str = "heuristic",  # NOT "full_rollout"
) -> SimulationResult:
    """Lightweight simulation of the counterfactual.
    
    Heuristic mode (fast, cheap):
    - Check if the edit would change routing decisions
    - Check if the edit would add/remove tool calls
    - Check if the edit addresses the failure mechanism
    - Estimate whether the final output would change
    
    This is NOT a full rollout. It's a sanity check.
    Full validation happens in evaluation.py after submission.
    """
```

The heuristic simulation can check:
- **Routing impact**: Would the edit change which node the agent routes to?
- **Tool impact**: Would the edit cause different tool calls?
- **Mechanism alignment**: Does the edit address the specific failure mechanism identified by the analyzer?
- **Regression risk**: Does the edit touch artifacts used by other successful tasks?

## VI. The Efficiency Design

You asked for an "ideal and efficient" editor. Here's how to keep it efficient:

### Cost Control

| Component | Cost | Mitigation |
|---|---|---|
| Understanding (trace reading) | Low — reads cached trace | Use selective subgraph reading, not full trace |
| Learning (edit history) | Low — bounded RAG retrieval | Cap at 5 similar edits |
| Proposing (draft edit) | Medium — 1 LLM call | Single structured output |
| Simulating (counterfactual) | **High if full rollout** | **Use heuristic mode only** |
| Committing | Low — structured submission | No LLM call needed |

**The key efficiency rule:** The editor's simulation is a **heuristic pre-filter**, not a full validation. Full validation is done by `evaluation.py` after the edit is submitted. This keeps the editor fast (2-4 LLM calls per edit) while still catching obvious problems before wasting a rollout.

### Bounded Retrieval

The `search_edit_history` tool must be bounded:
- Maximum 5 similar edits retrieved
- Maximum 1000 tokens per edit summary
- Only retrieve edits for the same artifact or same mechanism cluster
- Never retrieve raw prompts, raw responses, or expected answers

### Early Termination

The editor should terminate early if:
- The issue has exhausted its retry budget (3 attempts)
- The artifact has no writable surface
- The edit history shows 3 consecutive failures on this issue
- The simulation predicts a regression with high confidence

## VIII. My Additional Recommendations

### 1. Start Without Simulation, Add It Later

The simulation capability (Phase 4) is the most complex part. I recommend:
- **Phase A**: Implement the editor with tools for Phases 1, 2, 3, and 5 (understand, learn, propose, commit). Skip simulation.
- **Phase B**: Add the tag-based tentative state construction.
- **Phase C**: Add the lightweight counterfactual simulation.

This lets you get a working editor quickly, then enhance it.

### 2. The Tag System Should Be in the Wrapper, Not the Editor

The tag injection should happen in `materialize_harness()` in the wrapper, not in the editor. The editor just reads the tags from the trace. This keeps the editor focused on editing, not on harness construction.

### 3. Use the Existing `memory.py` for RAG, Don't Build a New One

The architecture already defines `memory.py` with append-only, redacted, bounded retrieval. The editor's `search_edit_history` tool should query this existing store, not build a separate vector database.

### 4. The Editor Should Produce Structured Output

The editor agent should output a structured `EditPlan`, not free-form text:

```json
{
    "edits": [
        {
            "artifact_id": "skills/retrieval-recovery",
            "operation": "append_section",
            "payload": {
                "heading": "## Checksum Verification",
                "content": "Before reporting the final answer, verify..."
            }
        }
    ],
    "rationale": "The agent failed to verify checksums before reporting.",
    "risks": ["May add latency to the final answer step"],
    "expected_effect": {
        "mechanism_cluster_refs": ["cluster-checksum-verification"]
    },
    "simulation_result": {
        "routing_impact": "none",
        "tool_impact": "none", 
        "mechanism_alignment": 0.85,
        "regression_risk": 0.1
    }
}
```

### 5. The Editor Should Be Able to Say "No"

The most important capability of the editor is knowing when NOT to edit. If:
- The issue is `insufficient_evidence`
- The artifact has no clear connection to the failure
- The edit history shows repeated failures
- The simulation predicts a regression

The editor should return a `no_op` response with a clear rationale. This prevents wasted rollouts and protects the pool from bad edits.
