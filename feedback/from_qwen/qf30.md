# Verification Report: Unified CUGA Editor Agent Design

## Overall Verdict: **APPROVED with 3 required actions and 4 tracked risks**

The spec is architecturally sound, honestly documents its deviations, and maintains the critical safety boundaries. It correctly solves the most dangerous problem in the codebase: `FakeEditor` injecting expected answers into artifacts. However, there are three items that must be addressed before implementation, and four risks that must be actively tracked.

---

## I. Architecture Compliance Verification

### ✅ Agent Neutrality Maintained

The spec correctly places `CugaEditorAgent` in `adapters/`, not `core/`. The `Editor` protocol in `core/editor.py` is unchanged. The three invariants are well-defined:

1. `CugaEditorAgent.propose_edit(request) -> EditorResponse` satisfies the existing protocol
2. `repair_once_then_classify` continues to work unmodified
3. Tools close over the request, not over global state

This means `core/` never learns that the editor is a CUGA agent. The Phase 1-4 modules (`issues.py`, `evaluation.py`, `memory.py`, `pool.py`) are untouched.

### ✅ Write Authorization Defense-in-Depth

Authorization is enforced at two independent levels:
- **Tool body**: `stage_replace` and `stage_create` validate authorization immediately, giving the agent per-artifact feedback during its work
- **Post-hoc**: `validate_editor_plan` re-checks the complete staged set after finalization

This matches the architecture mandate: *"The adapter independently rejects edits outside the authorized set."*

### ✅ Evidence Boundary Correctly Excludes Answers

The editor never receives:
- `task.expected_contract` — the expected answer
- `trace.final_output` — frequently contains or hints at the expected answer
- Payload blobs — raw prompts and AgentState

The contamination guard (§8) adds a fail-closed scan of `tool_call` payloads for `expected_contract` string values. This is a meaningful addition because key-name denylisting alone cannot catch an expected answer appearing as free text inside a tool result.

### ✅ Provenance From Tool Execution, Not Narration

`parent_ids` is derived from `read_parent_artifact` tool-execution evidence, not from the agent's prose. This follows the same principle that makes `ingest_sdk_tool_calls` correct: **trust tool-body execution, not model narration.** The primary parent is always included; donors appear only if actually read.

### ✅ Outcome Taxonomy Distinguishes Failure Modes

The `no_tool_call` vs `no_op` distinction is critical and well-motivated:
- `no_tool_call`: The agent did not engage (produced prose, or staged without finalizing)
- `no_op`: The agent explicitly judged no edit warranted, with rationale

Collapsing these would let "the agent did not engage" masquerade as "the agent judged no edit warranted" — the same category of error that produced the retracted Phase 8 E2E PASS.

### ✅ Backward Compatibility

`EditorRequest` gains optional fields with defaults:
```python
parents: tuple[ParentContext, ...] = ()
```
Since it's a frozen dataclass, this is backward-compatible. Existing tests and `FakeEditor` continue to work untouched.

## II. Required Actions Before Implementation

### Action 1: Add Explicit Editor Budget Cap

The spec identifies this in §12 but does not resolve it:

> *"Editor calls are counted but never capped. `BudgetUsage.editor_calls` exists (`config.py:49`) but `reserve()`'s `limit_fields` map has no entry for it (`config.py:57-63`). With each editor call becoming 10–40 internal LLM calls, an explicit budget limit should follow."*

**This must be resolved before running experiments.** Without a cap, a single GEPA loop of 20 attempts could consume 200-800 internal LLM calls just for editing. Add `max_editor_calls` to `BudgetLimits` and wire it into `reserve()`.

### Action 2: Define Creation Namespace Policy and Cap

The spec states that artifact creation is "allowed, namespaced and capped" but defers the concrete values:

> *"What is the creation namespace policy and cap value? The design fixes that both exist and are enforced in the tool body; the concrete prefix set and numeric cap are implementation decisions to confirm."*

**Define these before implementation.** Suggested defaults:
- Namespace prefix: `generated/` (all created artifacts must start with this prefix)
- Per-attempt cap: 2 (maximum 2 new artifacts per edit attempt)
- Total pool cap: Track created artifacts across the pool and reject creation if the pool already has N generated artifacts

### Action 3: Verify `lineage_of` Handles Multiple Parents

The spec claims:

> *"`lineage_of` (`editor.py:484-492`) already accepts multiple parent versions and joins them sorted, so retry-budget scoping needs no change."*

**Verify this claim with a test before implementation.** If `lineage_of` only handles a single parent version, the retry budget scoping will break for crossover edits that draw from multiple parents.

## III. Tracked Risks

### Risk 1: Free-Form Crossover Bypasses Merge Provenance (HIGH)

The spec deliberately deviates from `merge-resolution.md`:

> *"Free-form crossover bypasses `merge-resolution.md:96-104`, which mandates deterministic three-way inheritance with the LLM receiving only a single tied conflicting artifact's ancestor/left/right content."*

**Consequence:** `MergeProvenance` and `ArtifactMergeDecision` are unused on this path. Per-artifact three-way provenance is replaced by observed-parent lineage. This means:
- No per-artifact inheritance record (ancestor/left/right/shared/refined)
- No complementarity score
- No deterministic merge audit trail

**Mitigation:** The editor's edits still go through `evaluation.py`, which checks protected floors. The safety net is partially maintained. But for the paper, you must clearly document that crossover edits do not produce `MergeProvenance` records.

### Risk 2: merge.py Has Three Unfixed Defects (MEDIUM)

The spec documents three defects in `core/merge.py`:
1. Identical parent edits misclassified as conflicts (`merge.py:335` never compares left to right)
2. Evidence resolution rules 1-3 absent (every conflict reaches an LLM)
3. `_blame_for_artifact` (`merge.py:250`) sums raw blame instead of computing `severity * confidence * score`
4. `plan_merge:305` drops artifacts absent from base with `continue` (lossy hole)

**Mitigation:** `plan_merge` has zero production callers, so none of this is currently reachable. But if Phase 5 merge is ever activated, these must be fixed first. Track this as a Phase 5 prerequisite.

### Risk 3: CUGA Process-Global State Sharing (MEDIUM)

The editor agent runs in the same process as rollout agents. The singleton `ActivityTracker` (`tracker.py:92-94`) and the global policy DB are shared.

**Mitigation:** The spec adds an isolation regression test that asserts the editor agent's own LLM calls never appear in a rollout trace. If a future CUGA version breaks the same-process assumption, the test fails rather than an experiment silently passing.

### Risk 4: Tool Invocation Reliability Unproven (HIGH)

The spec honestly documents:

> *"In isolated live runs the model stopped at ~92 completion tokens with `finish_reason:"stop"` and never called `load_skill`. It may not call these tools either. This is why `no_tool_call` is a first-class recorded outcome rather than an anomaly."*

**Mitigation:** The `no_tool_call` outcome taxonomy handles this gracefully. But if the model consistently fails to call tools, the editor is effectively inert. The live verification script (§11) will reveal this immediately. If tool invocation fails consistently, you may need to:
- Switch to a model with better tool-calling reliability
- Use structured output mode instead of tool calls
- Fall back to a simpler single-LLM-call editor

## IV. Design Strengths Worth Preserving

### 1. Staging-Then-Finalizing Write Model

The `stage_replace` / `stage_create` / `list_staged` / `unstage` / `submit_edit_plan` flow is excellent. It gives the agent incremental feedback during its work rather than a single all-or-nothing rejection at the end. The agent can:
- Stage an edit, see it's authorized
- Stage another edit, see it's rejected
- Unstage the rejected edit
- Finalize with only the authorized edits

### 2. Terminal Submit Tool

Using `submit_edit_plan` as a terminal tool (rather than parsing the agent's prose) is the correct bet. The spec explicitly states:

> *"Bets on tool-body execution (proven live) rather than model narration (proven unreliable)."*

This is consistent with the Phase 7 tracing lesson: trust structured tool outputs, not free-form text.

### 3. Rejection-Not-Raising Design

`submit_edit_plan` returns a rejection rather than raising an exception:

> *"It returns a rejection rather than raising, so the agent can correct itself within the same run before the core's one-correction repair protocol is needed."*

This gives the agent a chance to self-correct without consuming the one-repair budget.

### 4. Deliberate Omissions Are Honest

The spec explicitly does NOT include:
- Simulation tools (`build_tentative_state`, `simulate_counterfactual`) — because the tag-injection scheme doesn't exist
- `validate_edit_syntax` / `preview_edit_effect` — because they're near-tautological for markdown replacement

This honesty prevents scope creep and keeps the implementation focused.
