## Verdict

Yes — Option 1 is the right call, and the capability boundary is largely correct. It aligns with the established rule in the target architecture ("never infer that generic trajectory events can be resumed") and with the `cuga_tracing_context.md` finding that `track_tool_calls` alone is insufficient. Go ahead with the design spec, but resolve the six issues below first, because three of them will force a rewrite if discovered after implementation.

## Critical issues (resolve before writing the spec)

### 1. Reconcile `core/trace.py` with the existing trace surface in `contracts.py`

`contracts.py` already defines `ExecutionTrace`, `TraceEvent`, `CheckpointDescriptor`, and the adapter methods `capture_trace()`, `supports_counterfactual_replay()`, `discover_checkpoints()`, `replay_from_checkpoint()`. Adding a parallel `trace.py` with `CausalTrace`, `TraceEvent`, `StateSnapshot` creates two competing trace schemas.

Decide explicitly one of:
- **(a)** `trace.py` is the canonical home and `contracts.py` re-exports/delegates to it (thin contracts, rich models in trace.py); or
- **(b)** `trace.py` only holds the *rich persisted* schema, and `contracts.py` keeps the *minimal adapter-facing* schema, with an explicit mapping function between them.

I recommend (b): the adapter protocol should stay minimal and stable, while the persisted causal schema can evolve. But the spec must state the mapping and forbid the adapter from returning the rich schema directly through `capture_trace()` unless you intend to change that contract.

### 2. State precisely what causal claims tool-only replay supports

This is the deepest issue. Recorded-environment tool replay makes the **environment** deterministic, but the **LLM remains stochastic**. A counterfactual of the form "if skill S changed, the outcome changes" is confounded by sampling noise unless you also control LLM determinism.

The spec should state that tool replay alone supports **deterministic validation replay** (re-run a task with fixed tool results to test an edit's effect), and that **causal counterfactual claims** additionally require one or more of:
- LLM determinism controls (temperature 0, fixed seed, prompt-cache reuse), and/or
- multi-rollout averaging (the existing `G` rollouts mechanism).

And you are right to keep `supports_counterfactual_replay() == False` for tool-only replay. But then name the positive capability explicitly — e.g. `supports_recorded_environment_replay()` — so downstream code (generalization probes, focused validation) can actually *use* tool replay without falsely claiming checkpoint replay. Right now the proposal describes the replay boundary but doesn't name the capability gate that enables it.

### 3. Sanitization-by-default can starve causal attribution

Raw LLM prompts, outputs, and graph state are opt-in. But causal blame attribution (the core research contribution) often *requires* the reasoning content to attribute a failure to a specific artifact/phase. If the default trace strips reasoning, the analyzer/judge has thin evidence and blame graphs degrade.

Resolve the tension explicitly in the spec:
- Define a "causal-sufficient" sanitization level that preserves reasoning structure (which phase/tool/decision produced what) while redacting secrets and expected answers.
- Make the research default *causal-sufficient*, not *maximally redacted*. Maximally-redacted traces are for distribution, not for the internal analysis loop.

Otherwise you will build a privacy-safe trace that is too poor to drive H2 (causal-blame-directed editing).

## Important issues (resolve in the spec)

### 4. Graph history must be captured *during* execution, not only queried after

You write "query only verified graph APIs after execution to collect available state/history." LangGraph state history is only available if a **checkpointer was attached during the run**. Querying `agent.graph` after the fact returns the final state, and `get_state_history()` returns nothing if no checkpointer was active. 

So the spec needs a capability test: does the installed CUGA SDK attach a checkpointer to `agent.graph` by default? If not, graph snapshots will be empty and the manifest must record "graph_history: unavailable_no_checkpointer" — which is honest, but it means Option 1 ships with *no* state snapshots until Option 3 is verified. That's fine, but make it explicit so nobody assumes checkpoints exist.

### 5. Replay matching must be sequence-aware, not just content-aware

Your replay rule is "exact tool name plus canonicalized arguments must match." But a task may legitimately call the same tool twice with identical arguments. Content-only matching would then be ambiguous. Your directory layout (`<sequence>-<tool>.json`) already implies sequence awareness, but the matching rule omits it.

Fix the rule to match on **(sequence position, tool name, canonicalized arguments)**, and define canonicalization precisely (stable key ordering, float handling, nested normalization). Brittle canonicalization is the most common cause of replay failures — specify it now.

### 6. thread_id provenance

You say "generate a wrapper-owned run_id and stable thread_id." Clarify where the stable thread_id comes from and how it relates to LangGraph's thread_id (which keys the checkpoint chain). If the wrapper generates it, it must be injected consistently into whatever graph invocation is used, and recorded in the manifest. If it's derived from CUGA, record its source. Ambiguity here breaks checkpoint correlation later.

## Minor issues / additions

- **Correlation key for tracker/Langfuse/OpenLit:** if you record observability correlation metadata, define the shared span/trace ID that links a wrapper event to a Langfuse span. Without it, correlation is unjoinable.
- **Runtime capability detection:** you rely on tests to prove SDK behavior, which is right for CI. But also record a runtime `TraceCapabilities` snapshot of what the *installed* SDK actually exposed for *this* run (stream? graph? tracker?), because the installed version can differ from the tested version. You list `TraceCapabilities` as a model — good — just make it a runtime-detected, persisted record, not a static config.
- **Tool results are the highest-risk persistence.** They're persisted raw subject to the ban list. Since tool results can echo evaluator internals or labels, consider an allowlist for high-risk tool categories (graders/verifiers) rather than relying solely on the recursive banlist. This matches the fail-closed posture.

## One thing that's exactly right and worth keeping

The distinction you drew — *"Recorded-environment tool replay alone is not claimed as checkpoint replay"* and *"report unavailable facilities explicitly instead of fabricating"* — is the correct discipline and the single most important guardrail in this design. It prevents the exact fabrication failure the architecture warns against. Keep it verbatim in the spec, and make it a testable assertion (a test that asserts `supports_counterfactual_replay()` is False and that an empty checkpoints/ dir is recorded as `unavailable`, not silently omitted).

## Summary

- **Option ranking is correct.** Option 1 now, Option 2 as additive observability references, Option 3 gated behind proven checkpointer injection.
- **Resolve before spec:** trace-schema reconciliation (#1), causal-claim scope of tool replay (#2), sanitization vs. attribution (#3).
- **Resolve in spec:** graph-history timing (#4), sequence-aware replay matching (#5), thread_id provenance (#6).
- **Add:** runtime `TraceCapabilities`, correlation key, and tool-result allowlisting for high-risk tools.

Once #1–#3 are pinned down, write the design spec. The capability boundary is sound; the risk is in the three conceptual seams, not the overall shape.
