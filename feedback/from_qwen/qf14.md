# Review: CUGA Causal Tracing Implementation Plan

## Overall Verdict

The plan is **well-structured, capability-honest, and architecturally sound** in its core design decisions. It correctly refuses to claim checkpoint replay, maintains the adapter boundary, and follows TDD discipline. However, it has **one internal contradiction**, **three significant gaps**, and **two assumptions that need explicit verification** before execution.

The plan is a **Phase 7 design document** being written ahead of its execution window. This is fine as planning, but Phases 1–6 are not yet complete, so this plan **cannot execute yet**.

---

## I. What Is Correct and Well-Designed

### 1. Capability Honesty Is Maintained Throughout
The plan consistently refuses to fabricate capabilities:
- `supports_counterfactual_replay()` remains `False`
- Graph history is reported as `unavailable_no_checkpointer`
- No LangGraph checkpointer is attached
- No checkpoint IDs are synthesized

This aligns with the architecture's mandate: "It must never infer that generic trajectory events can be resumed."

### 2. Rich Trace vs. Minimal Adapter Trace Separation
The plan correctly separates:
- `CausalTrace` (rich, persisted, wrapper-owned) in `core/trace.py`
- `ExecutionTrace` (minimal, adapter-facing) in `core/contracts.py`

The adapter only propagates `causal_trace_path` as a reference string. This preserves the agent-neutral core boundary.

### 3. Fail-Closed Replay Semantics
The replay mechanism matches `(sequence, tool_name, canonicalized_arguments)` and fails closed before live tool I/O. Truncated or withheld observations are replay-ineligible. This is the correct safety posture.

### 4. Thread ID Provenance
Generating `thread_id = run_id` at the wrapper level and injecting it into CUGA's invoke call is the right approach. The manifest records `thread_id_source: "wrapper_generated"` for auditability.

### 5. Disabled vs. Unavailable Distinction
The plan correctly distinguishes `disabled_by_config` from `unavailable_no_sdk_surface` and `unavailable_no_checkpointer`. This prevents misattribution of missing data.

### 6. TDD Discipline
Every task follows red → green → commit with tee-captured logs. The test-first approach is consistent.

---

## II. Internal Contradiction (Must Fix)

### Commit Discipline Conflict

**Global Constraints** state:
> "Do not commit unless the user explicitly asks for a commit."

But individual tasks explicitly instruct commits:
- Task 1 Step 5: "Commit the schema increment"
- Task 2 Step 6: "Commit the configuration and writer increment"
- Task 3 Step 5: "Commit the recorder increment"
- Task 4 Step 5: "Commit the runtime integration increment"
- Task 5 Step 5: "Commit the runner wiring"
- Task 6 Step 5: "Commit the adapter-boundary assertion"
- Task 7 Step 5: "Commit verified implementation and evidence documentation"

**Resolution:** Either remove the global "do not commit" constraint and replace it with "commit at task boundaries after green tests pass," or remove all commit steps from individual tasks and add a single final commit instruction. The current state is contradictory and will confuse the executing agent.

## III. Significant Gaps

### Gap 1: Graph State Checkpoints Are Not Delivered

The plan explicitly states:
> "Do not attach a LangGraph checkpointer in this increment."

And:
> "Never synthesize checkpoint IDs, attach a checkpointer, call undocumented graph internals, or call graph history a replay-safe checkpoint chain."

This means the **primary value proposition** from `cuga_tracing_context.md` — state snapshots for counterfactual branching — is **not delivered** by this plan. The plan delivers:

| Capability | Delivered? |
|---|---|
| Tool observations with arguments/results | ✅ Yes |
| Stream events | ⚠️ Maybe (depends on SDK verification) |
| Thread ID tracking | ✅ Yes |
| LLM call capture | ⚠️ Only via Langfuse/OpenLit if configured |
| Graph state checkpoints | ❌ No |
| Counterfactual branching from checkpoints | ❌ No |
| Recorded-environment tool replay | ✅ Yes |

This is **honest and correct** for the current scope, but the plan should explicitly state what research questions this enables vs. doesn't enable:

**Enables:**
- Causal blame graph construction from tool/LLM event traces (H2)
- Deterministic tool replay for validation probes
- Trace-based analysis for the GEPA judge

**Does NOT enable:**
- Counterfactual branching from arbitrary state checkpoints
- "What if the agent had different memory at decision point X?"
- Replay from mid-execution with modified artifacts

The plan should add a section: "Research Capability Boundary" that explicitly states this.

### Gap 2: Payload Level Definitions Are Imprecise

The plan defines three payload levels: `structural`, `causal_sufficient`, `raw_opt_in`. But it does not precisely define what fields are preserved at each level.

The `cuga_tracing_context.md` discusses this conceptually but the plan needs to pin it down:

| Field | structural | causal_sufficient | raw_opt_in |
|---|---|---|---|
| Event type, sequence, timestamps | ✅ | ✅ | ✅ |
| Node/phase identifiers | ✅ | ✅ | ✅ |
| Tool name, canonical arguments | ✅ | ✅ | ✅ |
| Tool results | ❌ | ✅ (redacted) | ✅ (redacted) |
| LLM reasoning content | ❌ | ✅ (redacted) | ✅ (redacted) |
| LLM prompts | ❌ | ❌ | ✅ (redacted) |
| Graph state values | ❌ | ✅ (redacted) | ✅ (redacted) |
| Raw trace bodies | ❌ | ❌ | ✅ (redacted, opt-in) |

Without this table, the executing agent will make arbitrary decisions about what to include.

### Gap 3: No Trace Size Management

The plan writes `events.jsonl` as a split file but specifies no size limit. For long-running agents with many LLM calls and tool invocations, this file could grow to hundreds of megabytes. The plan should specify:
- Maximum events per trace before rotation or truncation
- Whether events.jsonl uses append-only or bounded-write semantics
- How the manifest records truncation if it occurs

## IV. Assumptions Requiring Explicit Verification

### Assumption 1: CUGA's `invoke()` Accepts `thread_id`

Task 4 Step 3 hardcodes:
```python
result = asyncio.run(agent.invoke(message, thread_id=thread_id, track_tool_calls=True))
```

But does the installed CUGA SDK actually accept `thread_id` as a parameter to `invoke()`? Task 0 Step 2 verifies the SDK surface:
```python
print(inspect.signature(CugaAgent.invoke))
```

But the implementation in Task 4 assumes the signature includes `thread_id`. If it doesn't, the entire thread provenance mechanism breaks. The plan should add a conditional: if `thread_id` is not in the invoke signature, generate the thread ID but do not inject it, and record `thread_id_source: "wrapper_generated_not_injected"`.

### Assumption 2: Stream Events Are Reducible to Stable Events

Task 4 Step 3 says:
> "Use `agent.stream()` only after its fake-agent test proves the expected yielded shape and ordering. If stream semantics cannot be reduced to a stable public normalized event, set `stream_events` to `unavailable_no_sdk_surface` or `runtime_failure`."

This is correct but the plan doesn't specify what "stable public normalized event" means. The executing agent needs a concrete schema for what a stream event looks like after normalization. Without this, the agent will invent a schema.

## V. Missing Integration Points

### 1. How Does CausalTrace Connect to the GEPA Judge?

The architecture (Section 5.4) says the judge receives "a selected rollout, relevant group analysis, task contract, artifact inventory, and a strict schema." The tracing plan produces a `CausalTrace`, but doesn't specify how the judge consumes it.

The plan should add a note: "The CausalTrace is consumed by later phases (Phase 3: evidence/diagnosis). This plan does not implement judge integration. The trace is persisted and available by reference."

### 2. How Does This Connect to the Score Tensor?

The architecture's score tensor (Section 4.4) requires `verdict_ids` and provenance. The trace produces events, but the connection between trace events and score cells isn't specified. This is a Phase 3+ concern but worth noting in the plan's scope boundary.

### 3. Ollama/Embedding Configuration

The architecture mentions `GEPA_MECHANISM_EMBEDDING_MODEL=embeddinggemma`. The tracing plan doesn't mention how trace embeddings (for verdict sampling diversity) would be computed. This is a Phase 3+ concern but the plan should explicitly exclude it.

## VI. Minor Issues

### 1. The `from None` vs `from error` Inconsistency

Task 1 Step 3 says safe factories should suppress exception chaining with `from None`. But the Step-2 config storage plan's Task 0 uses `from error` to preserve the chain for debugging. These are different phases with different needs, but the inconsistency should be documented.

### 2. Redaction Gateway Dependency Creates a Hard Block

Task 2 Step 4 says:
> "If a shared Phase-2 gateway exists when this plan executes, call it instead of duplicating its implementation. If it does not exist, stop implementation: Phase 7 cannot replace the binding Phase-2 persistence requirement with a local approximation."

This is correct but creates a hard dependency on Phase 2. Since Phase 2 is not yet complete, this plan **cannot execute** until Phase 2 passes. The plan should state this explicitly in the Phase Gate section.

### 3. The `max_observation_bytes` Truncation During Replay

The plan says truncated observations are "replay-ineligible" but doesn't explicitly test what happens when the replay engine encounters a truncated observation mid-sequence. It should fail closed, which the plan implies but doesn't test.

## VII. Summary

| Aspect | Verdict |
|---|---|
| Capability honesty | ✅ Excellent |
| Phase gate discipline | ✅ Correct (but cannot execute yet) |
| Adapter boundary preservation | ✅ Correct |
| Fail-closed replay | ✅ Correct |
| TDD discipline | ✅ Consistent |
| Commit discipline | ⚠️ Internal contradiction |
| Payload level definitions | ⚠️ Imprecise |
| Graph state checkpoints | ⚠️ Not delivered (honest, but limits research scope) |
| Trace size management | ⚠️ Missing |
| SDK assumptions | ⚠️ Need explicit verification |
| Judge integration | ⚠️ Missing (but correctly out of scope) |

**Verdict:** The plan is sound and ready to be saved as a Phase 7 design document. Fix the commit discipline contradiction, add the payload level table, add a "Research Capability Boundary" section, and add explicit notes about what this plan does and does not enable for causal analysis. Do not execute until Phases 1–6 pass their required tests.
