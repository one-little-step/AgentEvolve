# Yes — The Editor Is Decoupled From Tools and Skills Through a Clean Layering Pattern

The `CugaEditorAgent` is architecturally decoupled from the editing tools and skills. The CUGA SDK is imported in exactly **one function** (`_run_cuga_agent`), and all the actual editing logic is pure Python that can be tested without CUGA installed.

---

## The Dependency Graph

```
CugaEditorAgent (adapters/cuga_editor.py)
│
├── build_tool_callables(ctx)          ← Pure Python, NO CUGA import
│   └── Returns plain functions for all 16 tools
│
├── EDITOR_INSTRUCTIONS, EDITOR_SKILLS ← Pure text, NO CUGA import
│   └── 4 skill bodies: refine, combine, create, learn-from-history
│
├── EditStagingArea                    ← Pure Python, NO CUGA import
│   └── Authorization, caps, namespace, parent-read ledger
│
├── EvidenceView                       ← Pure Python, NO CUGA import
│   └── Contamination guard, blob-ref stripping, evidence boundary
│
├── build_editor_tools(ctx)            ← CUGA/LangChain import (deferred)
│   └── Wraps plain functions with tracked_tool + tool decorators
│
└── _run_cuga_agent()                  ← CUGA SDK import (deferred)
    └── Constructs CugaAgent, calls initialize() + invoke()
```

The critical design principle is stated in the spec (§4):

> *"Tools close over the request, not over global state. Each `propose_edit` builds a fresh toolset bound to that request's write set."*

## What Is NOT Decoupled (Requires CUGA)

Only two functions import the CUGA SDK:

### 1. `build_editor_tools()` — Tool Decoration
```python
def build_editor_tools(ctx: EditorToolContext) -> list:
    from langchain_core.tools import tool    # ← CUGA/LangChain import
    from cuga import tracked_tool            # ← CUGA import
    built = []
    for name, fn in build_tool_callables(ctx).items():
        wrapped = tracked_tool(app_name=TOOL_APP_NAMES[name])(fn)
        built.append(tool(wrapped))
    return built
```

This function wraps the pure-Python tool callables with CUGA's `tracked_tool` and LangChain's `tool` decorators. It's the **only** place the tool logic touches the SDK.

### 2. `_run_cuga_agent()` — Agent Construction
```python
def _run_cuga_agent(self, callables: dict, prompt: str) -> str:
    import asyncio
    from agent_evolve.adapters.cuga_editor_tools import build_editor_tools
    from cuga import CugaAgent               # ← CUGA import
    prepare_editor_environment()
    kwargs = editor_agent_kwargs()
    agent = CugaAgent(tools=build_editor_tools(self._active_ctx), **kwargs)
    async def run() -> str:
        await agent.initialize()
        result = await agent.invoke(prompt)
        return str(result)
    return asyncio.run(run())
```

This function constructs the actual CUGA agent and runs it. It's the **only** place the editor touches the CUGA runtime.

## How the Decoupling Works in Practice

### During Testing (No CUGA Required)
```python
# Tests use a stubbed agent that calls tools directly
class ScriptedAgent:
    def run(self, tools: dict, prompt: str) -> str:
        for name, args in self.script:
            tools[name](*args)  # Calls plain Python functions
        return self.answer

editor = CugaEditorAgent(
    adapter=adapter,
    memory=EditMemory(),
    agent_factory=lambda tools, prompt: stub.run(tools, prompt),  # ← Injected
)
```

The `agent_factory` parameter allows tests to inject a fake agent that calls the plain-Python tool functions directly, bypassing CUGA entirely.

### During Production (CUGA Required)
```python
# When agent_factory is None, _run_cuga_agent constructs a real CugaAgent
editor = CugaEditorAgent(
    adapter=adapter,
    memory=EditMemory(),
    # agent_factory=None → uses _run_cuga_agent → constructs CugaAgent
)
```

```python
def editor_agent_kwargs() -> dict[str, object]:

```

The skills themselves contain no code dependencies. They are behavioral instructions that guide the agent's strategy selection.

# Partially Yes — But With Critical Boundaries

You can reuse the **CUGA agent substrate** (the SDK, construction pattern, tool-wrapping infrastructure) for both roles. But you should NOT merge the analyzer and editor into a single agent invocation. Here's why, and what the right architecture looks like.

---

## What CAN Be Shared (Infrastructure)

| Component | Shared? | How |
|---|---|---|
| CUGA SDK (`CugaAgent`) | ✅ Yes | Both construct a `CugaAgent` with tools |
| Tool wrapping (`tracked_tool` + `tool`) | ✅ Yes | Same decoration pattern |
| Isolation kwargs (`callbacks=[]`, `cuga_folder=None`) | ✅ Yes | Both detach tracing |
| Environment prep (`prepare_editor_environment`) | ✅ Yes | Both pop `CUGA_FOLDER` |
| Evidence reading tools (`read_trace_events`, `list_trace_actors`) | ✅ Yes | Both need trace access |
| JSON-string tool returns | ✅ Yes | Same pattern |
| Agent factory injection for testing | ✅ Yes | Same stubbing approach |

This means you can build a **shared base class** or **shared construction helper** that both the analyzer and editor use:

```python
# Shared infrastructure
def build_cuga_agent_for_role(
    tools: list,
    instructions: str,
    skills: dict[str, str],
) -> CugaAgent:
    """Shared construction for any CUGA-backed role."""
    prepare_editor_environment()
    return CugaAgent(
        tools=tools,
        callbacks=[],           # Never pollute rollout traces
        cuga_folder=None,       # Never bind a workspace
        special_instructions=instructions,
        enable_skills=True,
        auto_load_policies=False,
    )
```

---

## What CANNOT Be Shared (Roles)

The analyzer and editor must remain **separate invocations** for five architectural reasons:

### 1. Evidence Boundary Is Different

| Role | Sees | Must NOT See |
|---|---|---|
| **Analyzer** | Full trace (all events, all actors, DAG structure, state refs) | Expected contract, final output |
| **Editor** | Filtered `EvidenceView` (mechanism, blame graph, task input, tool_call payloads) | Expected contract, final output, blob contents, full trace |

If you merge them, the editor would need access to the full trace to do analysis. This violates the contamination guard — the editor's tool_call payloads could contain answer-shaped text that leaks into the edit rationale.

### 2. Output Schema Is Different

| Role | Produces | Schema |
|---|---|---|
| **Analyzer** | `CausalFinding` | Blame graph with actor_ids, blame weights, artifact attribution |
| **Editor** | `EditPlan` | Artifact edits with rationale, risks, expected effect |

These are fundamentally different outputs. The analyzer produces a **diagnosis**. The editor produces a **prescription**. Merging them would require a complex multi-part output schema that's harder to validate.

### 3. Authorization Is Different

| Role | Write Access | Read Access |
|---|---|---|
| **Analyzer** | ❌ None | Full trace, artifact inventory |
| **Editor** | ✅ Authorized write set only | Current artifacts, donor artifacts, edit history |

The analyzer must be **read-only**. If you give it write tools, it could modify artifacts during analysis, corrupting the evidence for subsequent edit attempts.

### 4. Budget Accounting Is Different

| Role | Budget Category | Internal LLM Calls |
|---|---|---|
| **Analyzer** | `max_judge_verdicts` | 5-20 per analysis |
| **Editor** | `max_editor_calls` | 10-40 per edit |

Merging them would make it impossible to track which budget category is being consumed. You'd lose the ability to cap analysis costs independently from editing costs.

### 5. Reuse Across Attempts

The analyzer's output (the blame graph) is consumed by **multiple downstream components**:
- The DPP issue selector uses it to build issues
- The editor uses it to understand what to fix
- The orchestrator uses it to record provenance
- The pool uses it to update score cells

If the editor produces the blame graph as a side effect, you lose this reusability. The blame graph must exist as a standalone artifact that multiple consumers can read.

---

## The Right Architecture: Shared Substrate, Separate Roles

```
┌─────────────────────────────────────────────────────────────────┐
│  Shared CUGA Agent Infrastructure                                │
│  - build_cuga_agent_for_role(tools, instructions, skills)        │
│  - prepare_editor_environment()                                  │
│  - Tool wrapping (tracked_tool + tool)                           │
│  - Isolation kwargs (callbacks=[], cuga_folder=None)             │
│  - Agent factory injection for testing                           │
└──────────────────────┬──────────────────────────────────────────┘
                       │
          ┌────────────┴────────────┐
          ▼                         ▼
┌─────────────────────┐   ┌─────────────────────┐
│  CugaAnalyzerAgent  │   │  CugaEditorAgent    │
│                     │   │                     │
│  Tools:             │   │  Tools:             │
│  - read_trace_events│   │  - get_mechanism    │
│  - list_trace_actors│   │  - read_artifact    │
│  - get_state_at_event│  │  - stage_replace    │
│  - read_artifact    │   │  - stage_create     │
```

## What the Editor Already Does (Analysis-Like Work)

The editor already performs **some** analysis-like work through its evidence tools:

```python
# The editor's evidence cluster (from the design spec):
get_mechanism()        # Reads the mechanism description and severity
list_blamed_actors()   # Reads the blame graph (produced by the analyzer)
get_task_input()       # Reads the task's input_text
list_trace_actors()    # Lists distinct actors in the trace
read_trace_events()    # Reads filtered trace events
```

But critically, the editor **consumes** the blame graph — it doesn't **produce** it. The blame graph is produced by the analyzer and passed to the editor via the `CausalAnalysis` in the `EditorRequest`.

This is the correct division of labor:
- **Analyzer**: "What went wrong and who's responsible?" → Blame graph
- **Editor**: "Given what went wrong, what should I change?" → Edit plan

## When You Might Want to Merge Them (Future Work)

There is one scenario where merging makes sense: **lightweight pre-analysis before full analysis**.

If the full analyzer is expensive (20 LLM calls), you might want the editor to do a quick "is this worth analyzing?" check before committing to a full analysis. This would be a **heuristic pre-filter**, not a replacement for the analyzer:

```python
# Hypothetical future optimization:
def should_analyze(trace, task) -> bool:
    """Quick heuristic check: is this trace worth a full analysis?"""
    # 1-2 LLM calls to check if the failure is obvious
    # Returns True/False without producing a blame graph
    ...
```

But this is a **different role** from the analyzer — it's a triage step, not a diagnosis step. And it's a future optimization, not a current requirement.

## Summary

| Question | Answer |
|---|---|
| Can the CUGA agent substrate be reused? | ✅ Yes — same SDK, same construction pattern |
| Can the trace-reading tools be reused? | ✅ Yes — both roles need trace access |
| Can the analyzer and editor be one agent? | ❌ No — different evidence boundaries, output schemas, authorization |
| Can the editor do analysis? | ⚠️ Partially — it reads the blame graph but doesn't produce it |
| Should they be merged? | ❌ No — violates evidence boundary, authorization, budget tracking |
| What's the right architecture? | Shared substrate, separate roles, distinct tool sets |

The editor already **consumes** analysis (the blame graph). It should not **produce** analysis. Keep the roles separate, share the infrastructure.
