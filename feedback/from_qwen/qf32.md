# Designing the Ideal CUGA Editor Agent

Your instinct is correct. The analyzer is the simpler replacement — it reads traces and produces blame graphs. The editor is the harder one because it must **reason about the consequences of its own edits before making them**. Let me design this properly.

---

## I. Why the Editor Is Fundamentally Harder Than the Analyzer

The analyzer is **observational**: it looks at what happened and explains it.

The editor is **interventional**: it must predict what *would* happen if it changed something. This requires:

1. Understanding the current state (what the analyzer found)
2. Learning from history (what worked/failed before)
3. Predicting consequences (what would happen if I edit X)
4. Validating predictions (would this actually improve things)

A single LLM call can do step 1. Steps 2-4 require **tools and multi-step reasoning**. This is exactly why a CUGA agent is the right architecture.

## IV. The Tag-Based Tentative State Construction (Your Key Insight)

Your idea of wrapping each editable artifact with a unique tag is the right approach. Here's how to implement it properly:

### Step 1: Tag Injection at Harness Materialization

When the wrapper materializes a harness, it injects unique tags into each artifact's content:

```python
def materialize_harness(harness_config, workspace_dir):
    for artifact_id, content in skills.items():
        tag = f"[ARTIFACT:{artifact_id}:{version_hash[:8]}]"
        tagged_content = f"{tag}\n{content}\n[/ARTIFACT:{artifact_id}]"
        # Write tagged content to workspace
        (workspace / "skills" / artifact_id).write_text(tagged_content)
```

### Step 2: Tag Recording in the Trace

When CUGA loads the harness, the tagged content appears in the agent's messages and state. The trace records which tags were loaded:

```python
# In the trace events:
{
    "event_id": "graph:4",
    "kind": "llm_call_start",
    "payload": {
        "messages_ref": "eba5adb8...",
        "loaded_artifacts": [
            "ARTIFACT:skills/retrieval-recovery:a3f7b2c1",
            "ARTIFACT:policies/execution:8d4e5f6a",
            "ARTIFACT:memory/task-context:1b2c3d4e"
        ]
    }
}
```

### Step 3: Tentative State Construction

The editor can now build a tentative state by:

1. **Finding the relevant checkpoint** in the trace where the artifact was used
2. **Extracting the agent's state** at that checkpoint
3. **Locating the tagged artifact content** in the state via regex
4. **Replacing the tagged content** with the proposed edit
5. **Simulating forward** from that modified state

```python
def build_tentative_state(
    trace_id: str,
    checkpoint_sequence: int,     # Which checkpoint to start from
    artifact_id: str,             # Which artifact to modify
    proposed_content: str,        # The new content
) -> TentativeState:
    """Construct the agent's state as if the edit were applied.
    
    1. Load the checkpoint state from the trace
    2. Find the tagged artifact content via regex:
       pattern = r'\[ARTIFACT:{artifact_id}:.*?\].*?\[/ARTIFACT:{artifact_id}\]'
    3. Replace the matched content with proposed_content
    4. Return the modified state
    """
```

### Step 4: Lightweight Counterfactual Simulation

**Critical constraint:** The editor should NOT run a full CUGA rollout for simulation. That's what `evaluation.py` does AFTER the edit is submitted. The editor's simulation is a **pre-filter** — a lightweight heuristic check.

```python
def simulate_counterfactual(
    tentative_state: TentativeState,
    task_id: str,
    simulation_mode: str = "heuristic",  # NOT "full_rollout"
) -> SimulationResult:
    """Lightweight simulation of the counterfactual.
    
    Heuristic mode (fast, cheap):
    - Check if the edit would change routing decisions
    - Check if the edit would add/remove tool calls
    - Check if the edit addresses the failure mechanism
    - Estimate whether the final output would change
    
    This is NOT a full rollout. It's a sanity check.
    Full validation happens in evaluation.py after submission.
    """
```

The heuristic simulation can check:
- **Routing impact**: Would the edit change which node the agent routes to?
- **Tool impact**: Would the edit cause different tool calls?
- **Mechanism alignment**: Does the edit address the specific failure mechanism identified by the analyzer?
- **Regression risk**: Does the edit touch artifacts used by other successful tasks?

## VI. The Efficiency Design

You asked for an "ideal and efficient" editor. Here's how to keep it efficient:

### Cost Control

| Component | Cost | Mitigation |
|---|---|---|
| Understanding (trace reading) | Low — reads cached trace | Use selective subgraph reading, not full trace |
| Learning (edit history) | Low — bounded RAG retrieval | Cap at 5 similar edits |
| Proposing (draft edit) | Medium — 1 LLM call | Single structured output |
| Simulating (counterfactual) | **High if full rollout** | **Use heuristic mode only** |
| Committing | Low — structured submission | No LLM call needed |

**The key efficiency rule:** The editor's simulation is a **heuristic pre-filter**, not a full validation. Full validation is done by `evaluation.py` after the edit is submitted. This keeps the editor fast (2-4 LLM calls per edit) while still catching obvious problems before wasting a rollout.

### Bounded Retrieval

The `search_edit_history` tool must be bounded:
- Maximum 5 similar edits retrieved
- Maximum 1000 tokens per edit summary
- Only retrieve edits for the same artifact or same mechanism cluster
- Never retrieve raw prompts, raw responses, or expected answers

### Early Termination

The editor should terminate early if:
- The issue has exhausted its retry budget (3 attempts)
- The artifact has no writable surface
- The edit history shows 3 consecutive failures on this issue
- The simulation predicts a regression with high confidence

## VIII. My Additional Recommendations

### 1. Start Without Simulation, Add It Later

The simulation capability (Phase 4) is the most complex part. I recommend:
- **Phase A**: Implement the editor with tools for Phases 1, 2, 3, and 5 (understand, learn, propose, commit). Skip simulation.
- **Phase B**: Add the tag-based tentative state construction.
- **Phase C**: Add the lightweight counterfactual simulation.

This lets you get a working editor quickly, then enhance it.

### 2. The Tag System Should Be in the Wrapper, Not the Editor

The tag injection should happen in `materialize_harness()` in the wrapper, not in the editor. The editor just reads the tags from the trace. This keeps the editor focused on editing, not on harness construction.

### 3. Use the Existing `memory.py` for RAG, Don't Build a New One

The architecture already defines `memory.py` with append-only, redacted, bounded retrieval. The editor's `search_edit_history` tool should query this existing store, not build a separate vector database.

### 4. The Editor Should Produce Structured Output

The editor agent should output a structured `EditPlan`, not free-form text:

```json
{
    "edits": [
        {
            "artifact_id": "skills/retrieval-recovery",
            "operation": "append_section",
            "payload": {
                "heading": "## Checksum Verification",
                "content": "Before reporting the final answer, verify..."
            }
        }
    ],
    "rationale": "The agent failed to verify checksums before reporting.",
    "risks": ["May add latency to the final answer step"],
    "expected_effect": {
        "mechanism_cluster_refs": ["cluster-checksum-verification"]
    },
    "simulation_result": {
        "routing_impact": "none",
        "tool_impact": "none", 
        "mechanism_alignment": 0.85,
        "regression_risk": 0.1
    }
}
```

### 5. The Editor Should Be Able to Say "No"

The most important capability of the editor is knowing when NOT to edit. If:
- The issue is `insufficient_evidence`
- The artifact has no clear connection to the failure
- The edit history shows repeated failures
- The simulation predicts a regression

The editor should return a `no_op` response with a clear rationale. This prevents wasted rollouts and protects the pool from bad edits.
