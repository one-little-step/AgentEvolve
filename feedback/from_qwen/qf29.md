# The Editor Does ONLY Mutation. Crossover Is a Separate Phase 5 Operation.

## What the Editor Actually Does (Mutation)

The editor takes **one parent**, reads its artifacts, and proposes targeted edits based on the causal finding. This is single-parent mutation:

```python
# In SequentialGepaRunner.run_attempt():
parent = self.select_parent()              # ONE parent selected
issue = selected[0]                        # ONE issue selected
workspace, response, corrections = self.propose_edits(
    parent, issue, task, analysis, attempt_id
)
```

The `EditorRequest` confirms this — it receives a single `base_workspace`:

```python
@dataclass(frozen=True, slots=True)
class EditorRequest:
    base_workspace: CandidateWorkspace      # ONE parent
    task: EvolutionTask
    analysis: CausalAnalysis               # The causal finding
    issue_id: str
    write_set: tuple[str, ...]             # Artifacts the editor CAN touch
    current_artifacts: Mapping[str, str]   # Current content of ONE parent
    history_refs: tuple[str, ...] = ()     # Past attempts (RAG, not crossover)
```

The editor proposes edits to **one parent's artifacts**. It never receives two parents to combine.

## What Handles Crossover (Phase 5: `merge.py`)

Crossover is a **completely separate operation** handled by the merge module. It takes **two parents** and an **ancestor**, and combines their artifacts:

```
Three-Way Merge:
    Ancestor (common ancestor)
        ├── Left parent  (candidate A)
        └── Right parent (candidate B)
              │
              ▼
        Per-artifact inheritance decision:
            ancestor | left | right | shared | refined
              │
              ▼
        Child candidate (merged artifacts)
```

From `merge-resolution.md`:
> *"Per-artifact three-way provenance is mandatory. Each artifact decision records ancestor_hash, left_hash, right_hash, resulting_hash, inheritance type, evidence scores, and decision reason."*

This is Phase 5 work and is currently in **prototype state** — it is NOT architecture-compliant and NOT wired into the GEPA loop.

## The Two Paths to New Candidates

```
Path 1: MUTATION (Editor — Phase 4, IMPLEMENTED)
    Parent + Issue + CausalFinding
        → Editor proposes edits
        → Validate (origin + regression probes)
        → Accept/Reject
        → New candidate in pool

Path 2: CROSSOVER (Merge — Phase 5, PROTOTYPE ONLY)
    Parent A + Parent B + Ancestor
        → Three-way merge per artifact
        → Complementarity scoring
        → Eligibility checks
        → Validate merged candidate
        → New candidate in pool
```

Both paths produce new candidates for the persistent pool. But they are architecturally distinct operations with different protocols, different validation, and different provenance recording.

---

## The `history_refs` Is NOT Crossover

You might notice the editor receives `history_refs` (previous edit attempts). This is **RAG-based learning**, not crossover:

```python
history_refs=tuple(
    a.attempt_id for a in self.edit_memory.for_issue(issue_id)
)
```

The editor reads past attempts to learn "what was tried before and what worked/failed." It does NOT read artifacts from another parent candidate. This is the edit memory RAG mandated by the architecture:

> *"Edit memory records worked, failed, and regression state. Retrieval is bounded and references only sanitized records."*
