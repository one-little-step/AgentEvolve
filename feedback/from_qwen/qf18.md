# Review: Phase 1–4 Research Core Design

## Overall Verdict

**Approve with three required revisions.** The design is well-structured, correctly prioritizes research-critical algorithms, and maintains the binding contract boundaries. The Phase 4 internal ordering is correct. The storage exception is reasonable for research but needs proper authorization. Three gaps must be closed before implementation begins.

---

## I. What Is Correct and Well-Designed

### 1. Research Storage Exception Is Honest and Bounded
The design explicitly acknowledges the deviation from the SQLite WAL mandate:

> "This design uses `JSONFileStorage` despite the production SQLite WAL mandate in `docs/architecture/storage-and-transactions.md`."

It correctly limits the exception:
- Single-threaded Phase 1–4 research runs only
- Per-record temp-write-then-rename atomicity
- No multi-record transactions, recovery, blobs, or persistent leases
- `parallel_execution` is rejected while this backend is active
- Deferred production work is documented

This is the right tradeoff for research. The algorithms are the contribution, not the storage engine.

### 2. Phase 4 Internal Ordering Is Correct
The mandatory implementation order within Phase 4 is:

```
entropy.py → issues.py → memory.py → editor.py → evaluation.py
```

This follows the dependency chain correctly. Each module has its own TDD cycle. This prevents the agent from trying to implement all five modules simultaneously.

### 3. DPP Implementation Is Mandated, Not Approximated
The design correctly requires:
- Hierarchical DPP (tasks first, then mechanism clusters)
- Greedy MAP with Cholesky-style Schur-complement updates
- Kernel: `L = Q S Q + JITTER * I`
- Prefilter to `GEPA_DPP_MAX_ITEMS` before dense kernel
- All four selection modes: `dpp`, `severity_rank`, `coverage`, `random`
- Deterministic tie-breaking by ascending stable issue ID
- Explicit fallback reasons for missing/malformed embeddings

This is the full mandated DPP, not a severity-only placeholder.

### 4. Entropy Implementation Matches the Architecture
The design specifies:
- Population variance with score-floor scaling: `entropy = variance * max(max_score, GEPA_ENTROPY_SCORE_FLOOR)`
- Evidence floors: 3 comparable candidates, 2 rollouts per candidate
- Frontier cells below recombination threshold retain configured frontier weight
- Incremental statistics: count, sum, sum of squares, candidate score map, maximum score/owner, rollout counts, cluster freshness
- Heap operations deterministic and run only at sequential barrier

This matches Section 7.0 of the target architecture.

### 5. Generalization Probes Are Correctly Deferred
The design says:
> "Generalization is deferred by default: the result explicitly records `generalization_unverified`; it is neither omitted nor treated as passing."

This matches `GEPA_GENERALIZATION_PROBE_MODE=deferred` from the architecture.

### 6. Blame Graph Integrity Is Preserved
The design says:
> "Unknown, malformed, uncertain, and insufficient evidence remain explicit findings; no synthetic blame nodes or fixed taxonomy are allowed."

This directly addresses the prototype flaw identified in `f1.md` where the orchestrator fabricated synthetic blame nodes.

### 7. Prototype Migration Boundaries Are Explicit
The design clearly states what replaces what:
- Broad `entropy.py` selection ownership moves to `issues.py`
- Shallow caller-trusted sanitization becomes one recursive storage gateway
- Editor-owned floor/validation behavior moves to `evaluation.py`
- Direct orchestration edits without target-level authorization are replaced by editor validation plus adapter-enforced write scopes

### 8. Initial Experiment Is Correctly Specified
> "The first research result compares B0 and B1 on a fixed coreset with matched rollout budgets and at least three deterministic seeds."

This tests H1 and follows the research hypotheses protocol.

## II. Required Revisions

### Revision 1: Resolve the Contradictory Phase 2 Plans (Critical)

There are **two Phase 2 plans** in the repository:

| Document | Storage Backend | Status |
|---|---|---|
| `2026-08-12-step-2-config-storage-foundation.md` | SQLite WAL with ACID transactions | Mandated by enforcement design |
| `2026-08-12-phase-1-4-research-core-design.md` | JSONFileStorage | Research simplification |

The enforcement design (`2026-08-12-architecture-enforcement-design.md`) says:

> "core/storage.py must provide the mandated SQLite transactional metadata store."

The Phase 1–4 design says:

> "The exception is formally recorded in `2026-08-12-architecture-enforcement-design.md`."

**But the enforcement design does not actually grant this exception.** It still mandates SQLite.

**Resolution:** You must do one of the following:

**(a)** Update the enforcement design to explicitly grant the research storage exception:

```markdown
## Research Storage Exception (Approved)

For Phase 1–4 research runs with single-threaded execution and deterministic
fake adapters, JSONFileStorage is approved as a substitute for the SQLite WAL
mandate. This exception applies only when:
- parallel_execution is disabled
- All runs are single-threaded
- No concurrent writers exist
- The StorageBackend protocol is satisfied

The exception is revoked when Phase 5 (parallel execution) begins.
At that point, SQLite WAL or equivalent transactional storage is required.

This exception does NOT waive:
- Recursive fail-closed redaction
- Budget tracking
- Profile resolution
- Manifest serialization
```

**(b)** Or follow the Step-2 plan and use SQLite WAL from the start.

I recommend **(a)** because it saves significant implementation time and the research contribution is in the algorithms, not the storage. But the exception must be explicitly granted in the enforcement design, not merely referenced.

### Revision 2: Enumerate All Budget Fields Explicitly (Important)

The design says:

> "Budgets separately count rollouts, analyzer/judge calls, editor calls, validation calls, embedding calls, model tokens when supplied by an adapter, and attempts."

But the architecture (Section 3.2) mandates these specific budget fields:

```
GEPA_MAX_ATTEMPTS
GEPA_MAX_ACCEPTED_EDITS
GEPA_MAX_MODEL_TOKENS
GEPA_MAX_ROLLOUTS
GEPA_MAX_JUDGE_VERDICTS
GEPA_EDIT_MAX_RETRIES=3
GEPA_MAX_WALL_SECONDS
GEPA_MAX_POOL_CANDIDATES
GEPA_MAX_HISTORY_RECORDS
GEPA_MAX_RAG_CONTEXT_TOKENS
```

The design mentions "attempts" but does not explicitly list `max_accepted_edits`, `max_wall_seconds`, `max_pool_candidates`, `max_history_records`, or `max_rag_context_tokens`. The Step-2 plan's `BudgetLimits` dataclass includes all of these.

**Resolution:** Add the complete budget field enumeration to the Phase 2 config section:

```markdown
Budgets track these categories, matching the architecture mandate:
- max_attempts: total edit attempts
- max_accepted_edits: accepted edits (complexity budget)
- max_model_tokens: total model tokens across all roles
- max_rollouts: agent rollout executions
- max_judge_verdicts: analyzer/judge calls
- edit_max_retries: per-issue retry ceiling (default 3)
- max_wall_seconds: wall-clock time limit
- max_pool_candidates: persistent pool size bound (complexity budget)
- max_history_records: edit memory size bound (complexity budget)
- max_rag_context_tokens: editor context window bound (complexity budget)
- embedding_calls: embedding provider invocations
- validation_calls: focused validation rollout invocations
```

### Revision 3: Add Champion Selection and Parent Sampling Formulas (Important)

The design mentions `pool.py` owns "champion selection" and "parent sampling" but does not specify the formulas. The architecture mandates specific formulas:

**Parent sampling** (Section 6.3):
```
frequency(c) = Σ_{t,m} severity(t,m) × confidence(t,m) × 1[c wins (t,m)]
```

**Champion selection** (Section 6.4):
```
argmax_{h ∈ P} α·Outcome(h) + β·ProcessCoverage(h) + γ·Stability(h) − δ·RegressionRisk(h)
```

With defaults: α=0.55, β=0.20, γ=0.15, δ=0.10.

**Resolution:** Add these formulas to the Phase 3 pool section:

```markdown
Pool parent selection uses weighted objective coverage:
frequency(c) = Σ_{t,m} severity(t,m) × confidence(t,m) × 1[c wins (t,m)]

Champion selection uses the transparent aggregate:
argmax_{h ∈ P} α·Outcome(h) + β·ProcessCoverage(h) + γ·Stability(h) − δ·RegressionRisk(h)

Defaults: α=0.55, β=0.20, γ=0.15, δ=0.10.
Protected critical floors override this aggregate.
The manifest exposes every component and tie-breaker.
```

## III. Important Observations (Non-Blocking)

### 1. The "coverage" DPP Mode Is Not in the Main Architecture

The design lists four selection modes: `dpp`, `severity_rank`, `coverage`, `random`.

The main architecture (Section 7.2) lists three: `dpp`, `severity_rank`, `random`.

The `coverage` mode is defined in the DPP selector completion design (`2026-08-11-dpp-selector-completion-design.md`) as "deterministic farthest-first diversity-only selection." This is a valid addition but should be noted as an extension beyond the main architecture.

### 2. The Two-Tier Entropy Classification Should Be Explicit

The design mentions frontier cells but does not explicitly name all three tiers:
- `recombination_target`: max score exceeds `GEPA_ENTROPY_RECOMBINATION_SCORE_THRESHOLD`
- `frontier_exploration`: variance meaningful but max score below threshold; quality receives `GEPA_ENTROPY_FRONTIER_WEIGHT`
- `skip`: insufficient variance/evidence

The config values are listed (`GEPA_ENTROPY_RECOMBINATION_SCORE_THRESHOLD=0.30`, `GEPA_ENTROPY_FRONTIER_WEIGHT=0.30`), so the implementation should handle all three tiers. But the design should name them explicitly.

### 3. The Verdict Sampler Is Not Mentioned

The architecture (Section 5.3) describes a task-local rollout diversity sampler for judge budget. The Phase 1–4 design does not mention this. Since Phase 1–4 uses fake adapters, the verdict sampler may not be needed yet. But the design should note that it is deferred to a later phase.

### 4. Model Role Configuration Is Not Mentioned

The architecture (Section 5.1) defines three model roles: rollout agent, analyzer+judge, editor. The Phase 1–4 design does not mention model role configuration. Since Phase 1–4 uses fake adapters, this is acceptable. But the design should note that model role configuration is deferred to Phase 5+ when real models are used.

### 5. The Design Correctly Excludes Merge and Parallel

The design states:
> "CUGA, merge, parallel execution, and orchestration lifecycle changes are out of scope."

This is correct. Merge is Phase 5, parallel is Phase 5, orchestration is Phase 6, CUGA is Phases 7-8.

### 6. The Ollama Configuration Is Correctly Scoped

The design says:
> "The resolver reads `OLLAMA_EMBEDDING_URL` and `OLLAMA_EMBEDDING_MODEL` from the environment. They are endpoint/model configuration, not secrets. Phase 1–4 tests use lexical embeddings and make no Ollama network call."

This is correct. The Phase-1 contract completion design also says:
> "No HTTP request, reachability probe, embedding generation, vector storage, clustering, or semantic retrieval is allowed in Phase 1 or Phase 2."

### 7. The Redaction Gateway Is Correctly Centralized

The design says:
> "Every write passes through one recursive sanitizer... No caller may bypass this gateway."

This matches the architecture mandate and addresses the prototype flaw where `memory.py` only checked top-level keys.
