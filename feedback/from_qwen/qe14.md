# Review: CUGA Tracing Implementation-Level Design

## Overall Verdict

This is a **well-structured, capability-honest design** that correctly applies the discipline established in the architecture enforcement documents. The capability-gated approach, the distinction between "disabled by config" and "unavailable from SDK," and the fail-closed replay semantics are all correct. The design is substantially better than what the coding agent produced in earlier phases.

However, there are **six gaps** that should be addressed before this becomes a design spec. Three are critical, three are important.

---

## What Is Well-Designed

### 1. Capability Honesty Is Maintained Throughout
The design consistently refuses to fabricate capabilities:
- Stream observations captured "only if independently proven by focused tests"
- Graph state/history captured "only through verified public `agent.graph` methods"
- Without an active checkpointer, records "an explicit unavailability reason rather than pretending streamed values are replayable checkpoints"
- `supports_counterfactual_replay()` remains `False`

This is exactly the discipline that prevents the "docstring-driven deception" pattern from earlier phases.

### 2. The Disabled vs. Unavailable Distinction
> "A disabled optional facility is distinct from an SDK-unavailable one in `TraceCapabilities`."

This is important for research integrity. If a facility is disabled by config, the manifest should say "disabled_by_config." If the SDK doesn't expose it, the manifest should say "unavailable_no_sdk_surface." These have different implications for interpreting results.

### 3. Sequence-Aware Tool Observation Matching
The recorder "consumes exactly the observation at the same sequence number and rejects tool-name or argument mismatches without calling the underlying tool." This addresses the earlier concern about content-only matching being ambiguous when the same tool is called twice with identical arguments.

### 4. Rich Trace on Disk, Minimal View in Core
> "The rich trace stays on disk and is fetched by reference, avoiding an oversized or CUGA-shaped generic core contract."

This correctly preserves the agent-neutrality boundary. The core sees `ExecutionTrace` (minimal), the wrapper owns `CausalTrace` (rich). This is the right separation.

### 5. TDD With Comprehensive Test Coverage
The test list is thorough and precedes implementation. The specific test cases (fail-closed replay, capability states, payload filtering, high-risk tool withholding) directly target the failure modes that matter.

### 6. Backward Compatibility When Tracing Disabled
> "If tracing is disabled, no trace directory is created and the wrapper's normal return shape remains backward compatible."

This prevents tracing from becoming a mandatory dependency for existing workflows.

## Critical Gaps (Must Address Before Implementation)

### Gap 1: No Explicit Phase Gate Acknowledgment

The architecture enforcement design (`2026-08-12-architecture-enforcement-design.md`) establishes a hard phase gate:

> "No production changes may be made to a phase's modules until every preceding phase has passing tests for its binding requirements."

The CUGA wrapper is **Phase 7**. The CUGA adapter is **Phase 8**. Phases 1–6 must pass first.

The design says "This completes the implementation-level design" but does not explicitly state:
- This is Phase 7 work
- It is gated behind Phases 1–6 (contracts, config/storage, evidence/diagnosis, selection/editing, merge/parallel, orchestration)
- No implementation begins until those phases pass their required tests

**Recommendation:** Add an explicit phase-gate statement at the top of the design spec:

```
Phase: 7 (CUGA wrapper)
Prerequisites: Phases 1-6 must have passing tests for their binding requirements.
This design does not authorize implementation until the phase gate is satisfied.
```

### Gap 2: Recorded-Environment Replay Is Necessary but Not Sufficient for Causal Counterfactuals

The design handles **tool/environment determinism** through recorded observations. But causal counterfactual analysis requires **LLM determinism** as well. If the LLM is stochastic (temperature > 0, no cache, no seed), then replaying from a checkpoint with the same tool observations will still produce different LLM outputs, confounding the causal effect estimate.

The design should explicitly acknowledge:

> Recorded-environment replay eliminates tool/environment variance. It does not eliminate LLM sampling variance. Causal counterfactual claims additionally require LLM determinism controls (temperature 0, prompt cache reuse, or fixed seed) or multi-rollout averaging. These controls are a separate requirement from the tracing layer and must be configured at the rollout/adapter level.

This doesn't need to be implemented in the tracing layer, but the design spec should state it explicitly so that the causal analysis pipeline doesn't mistakenly assume recorded-environment replay alone is sufficient.

### Gap 3: Payload Level Definitions Are Unspecified

The design defines three payload levels:
- `structural`
- `causal_sufficient` (research default)
- `raw_opt_in`

But it does not specify **what fields are preserved at each level**. This is critical because:
- `causal_sufficient` must preserve enough reasoning content for the analyzer/judge to build causal blame graphs
- `structural` should preserve event structure but not raw content
- `raw_opt_in` should preserve everything, subject to the redaction gateway

**Recommendation:** Define the payload levels explicitly:

| Field | structural | causal_sufficient | raw_opt_in |
|---|---|---|---|
| Event type, sequence, timestamps | ✅ | ✅ | ✅ |
| Node/phase identifiers | ✅ | ✅ | ✅ |
| Tool name, arguments (canonicalized) | ✅ | ✅ | ✅ |
| Tool results | ❌ | ✅ (redacted) | ✅ (redacted) |
| LLM reasoning content | ❌ | ✅ (redacted) | ✅ (redacted) |
| LLM prompts | ❌ | ❌ | ✅ (redacted) |
| Graph state values | ❌ | ✅ (redacted) | ✅ (redacted) |
| Raw trace bodies | ❌ | ❌ | ✅ (redacted, opt-in) |

All levels pass through the redaction gateway. `raw_opt_in` requires explicit operator confirmation.

## Important Gaps (Should Address, Non-Blocking)

### Gap 4: Checkpointer Attachment Is Ambiguous

The design says:
> "captures graph state/history only through verified public `agent.graph` methods. Without an active checkpointer, it records an explicit unavailability reason."

But it does not clarify: **does the design include attaching a checkpointer to the graph, or does it only capture what's available?**

If the design only captures what's available, then `capture_graph_history` will always be `unavailable_no_checkpointer` unless CUGA attaches a checkpointer by default. This should be stated explicitly.

If the design includes attaching a checkpointer (e.g., `MemorySaver` or `SqliteSaver`), then it needs to specify:
- Which checkpointer is used
- How it's attached (via `agent.graph` compilation or CUGA config)
- Whether this requires SDK verification first

**Recommendation:** State explicitly:

> This design does not attach a checkpointer. It captures graph state/history only if CUGA's runtime already has an active checkpointer. If no checkpointer is active, `capture_graph_history` records `unavailable_no_checkpointer`. Attaching a checkpointer is a separate SDK verification task governed by `docs/architecture/cuga-adapter/sdk-verification-matrix.md`.

### Gap 5: Tool Observation Size Limits Are Unspecified

If tools return large results (web pages, database dumps, file contents), storing them raw in `observations/` could be expensive. The design should specify:
- Maximum observation size before truncation or withholding
- Whether truncation is recorded in the manifest
- Whether large observations are stored as blobs (content-addressed) rather than inline JSON

**Recommendation:** Add a `max_observation_bytes` config to `TraceConfig` with a sensible default (e.g., 1 MB). Observations exceeding this limit are truncated with a `truncated: true` flag and the original byte length recorded.

### Gap 6: Redaction Gateway Integration Is Implicit

The design mentions "payload filtering" but does not explicitly state that this filtering uses the same recursive fail-closed redaction gateway defined in `docs/architecture/storage-and-transactions.md` (or an equivalent). The architecture mandates:

> "All persistence must pass a recursive redaction gateway that fails closed."

The tracing layer persists tool observations, LLM outputs, and graph state. These must pass through the redaction gateway.

**Recommendation:** State explicitly:

> All persisted trace payloads pass through the recursive fail-closed redaction gateway defined in `docs/architecture/storage-and-transactions.md`. The wrapper may use a shared redaction utility from `core.storage` or an equivalent wrapper-local implementation that satisfies the same binding constraints. Prohibited material is rejected, not silently removed.

## Observations (Not Gaps, But Worth Noting)

### The Design Correctly Defers CUGA SDK Verification
> "live SDK smoke test only after source/signature tests establish the actual public semantics."

This is correct and aligns with the architecture's mandate that CUGA APIs must not be guessed. The design should reference the SDK verification matrix (`docs/architecture/cuga-adapter/sdk-verification-matrix.md`) explicitly.

### The Design Correctly Separates Wrapper and Adapter Concerns
The wrapper owns tracing. The adapter maps wrapper results to the generic `ExecutionTrace`. This is the right separation and preserves the agent-neutrality boundary.

### The Design Correctly Handles the "No Trace" Case
When tracing is disabled, no files are created and the return shape is backward compatible. This prevents tracing from becoming a hidden dependency.

## Summary: Approve With Revisions

| Aspect | Verdict |
|---|---|
| Capability honesty | ✅ Excellent |
| Disabled vs. unavailable distinction | ✅ Correct |
| Sequence-aware tool matching | ✅ Correct |
| Rich trace / minimal view separation | ✅ Correct |
| TDD approach | ✅ Comprehensive |
| Backward compatibility | ✅ Correct |
| Phase gate acknowledgment | ⚠️ Missing — add explicit statement |
| LLM determinism acknowledgment | ⚠️ Missing — add explicit statement |
| Payload level definitions | ⚠️ Missing — define field preservation per level |
| Checkpointer attachment clarity | ⚠️ Ambiguous — state explicitly |
| Tool observation size limits | ⚠️ Unspecified — add config |
| Redaction gateway integration | ⚠️ Implicit — make explicit |

**Verdict:** Approve the design direction. Address the three critical gaps (phase gate, LLM determinism, payload levels) before writing the design spec. Address the three important gaps (checkpointer, size limits, redaction) in the design spec. Then proceed to self-review and implementation planning.

The design is substantially better than earlier phases and demonstrates that the architecture enforcement discipline is working. The remaining gaps are specification completeness issues, not architectural errors.
