# Review: Phase 1–4 Research Core Implementation Plan

## Overall Verdict

**Approve with five required revisions.** This plan is a well-structured, research-focused implementation that correctly applies the simplification strategy. It follows the mandatory Phase 4 dependency order, uses TDD discipline, excludes out-of-scope modules, and includes a B0/B1 smoke harness for the first research result. However, there are five issues that must be addressed before execution begins.

---

## I. What Is Correct and Well-Designed

### 1. Research Simplification Is Correctly Applied
The plan uses `JSONFileStorage` instead of SQLite WAL, which is the approved research exception. It correctly limits this to single-threaded runs with `parallel_execution=False`:

> "The approved JSON storage exception applies only to single-threaded fake-adapter Phase 1-4 runs with `parallel_execution=False`; Phase 5 requires SQLite WAL or equivalent transactional storage."

This is the right tradeoff for research. The algorithms are the contribution, not the storage engine.

### 2. Mandatory Phase 4 Implementation Order Is Followed
The plan implements Phase 4 modules in the correct dependency order:

```
Task 7: entropy.py (statistics only)
Task 8: issues.py (DPP selection)
Task 9: memory.py (redacted records)
Task 10: editor.py (authorization)
Task 11: evaluation.py (validation)
```

This matches the design document's mandatory ordering.

### 3. TDD Discipline Is Maintained
Every task follows the red → green → verify pattern with tee-captured logs. This prevents the "docstring-driven deception" pattern from earlier phases.

### 4. Scope Boundaries Are Clear
The plan explicitly excludes:
- CUGA wrapper and adapter
- Merge/crossover
- Parallel execution
- Orchestration integration

And it correctly marks `research_parallel` as "configuration-only and inactive."

### 5. B0/B1 Smoke Harness Is Included
Task 12 creates a simplified B0/B1 comparison harness:

> "B0 keeps only its best initial candidate; B1 stores every initial candidate and derives a Pareto frontier from comparable fake-adapter evidence."

This is the "Phase 4.5 Initial Experiment Harness" that enables testing H1 without the full RHO pipeline. The plan correctly notes: "This is a smoke harness, not a claim of H1."

### 6. Budget Fields Are Complete
The `BudgetLimits` dataclass includes all required fields:
- `max_attempts`
- `max_accepted_edits`
- `max_model_tokens`
- `max_rollouts`
- `max_judge_verdicts`
- `edit_max_retries`
- `max_wall_seconds`
- `max_pool_candidates`
- `max_history_records`
- `max_rag_context_tokens`

This addresses the gap identified in the previous review.

### 7. DPP Implementation Is Mandated, Not Approximated
Task 8 implements the full hierarchical DPP with:
- Greedy MAP with Cholesky-style Schur-complement updates
- Quality normalization and theta exponent
- Prefilter at `GEPA_DPP_MAX_ITEMS`
- All four selection modes: `dpp`, `severity_rank`, `coverage`, `random`
- Deterministic tie-breaking by ascending stable issue ID
- Explicit fallback reasons

This is the correct, complete implementation.

### 8. Entropy Tiers Are Tested
Task 7 tests all three entropy tiers:
- `recombination_target`
- `frontier_exploration`
- `skip`

This matches the architecture's two-tier classification.

### 9. Generalization Probes Are Correctly Deferred
Task 11 implements deferred generalization probes:

> "Under deferred mode, create zero executed generalization cases with `generalization_unverified`; do not silently drop the category."

This matches the architecture's `GEPA_GENERALIZATION_PROBE_MODE=deferred` setting.

## II. Required Revisions

### Revision 1: Resolve the Storage Contradiction (Critical)

The Phase 1-4 plan uses `JSONFileStorage`, but the enforcement design (`2026-08-12-architecture-enforcement-design.md`) still mandates SQLite WAL:

> "core/storage.py must provide the mandated SQLite transactional metadata store."

The Phase 1-4 plan claims the JSON storage exception is "formally recorded" in the enforcement design, but the enforcement design does not actually grant this exception.

**Resolution:** Update the enforcement design to explicitly grant the JSON storage exception:

```markdown
## Research Storage Exception (Approved)

For Phase 1–4 research runs with single-threaded execution and deterministic
fake adapters, JSONFileStorage is approved as a substitute for the SQLite WAL
mandate. This exception applies only when:
- parallel_execution is disabled
- All runs are single-threaded
- No concurrent writers exist
- The StorageBackend protocol is satisfied

The exception is revoked when Phase 5 (parallel execution) begins.
At that point, SQLite WAL or equivalent transactional storage is required.

This exception does NOT waive:
- Recursive fail-closed redaction
- Budget tracking
- Profile resolution
- Manifest serialization
```

Without this update, the next reviewer will flag the JSON storage as a binding violation.

### Revision 4: Acknowledge the Contract Simplification (Important)

Task 1 uses standard Pydantic `ValidationError` instead of the typed domain errors mandated by the Phase-1 Contract Completion Design:

```python
def test_score_cell_rejects_blank_candidate_id() -> None:
    with pytest.raises(ValidationError, match="candidate_id"):
        ScoreCell(**score_cell_values(candidate_id=""))
```

The Phase-1 Contract Completion Design mandates:

> "Persisted contracts expose only explicit safe construction factories... These factories... raise typed redacted domain errors..."

The Phase 1-4 plan has deliberately simplified this to use standard Pydantic behavior. This is consistent with the "Option 2: Accept all standard Pydantic behavior" decision discussed earlier.

**Resolution:** Add an explicit acknowledgment to the plan:

```markdown
## Contract Simplification (Research Exception)

This plan uses standard Pydantic validation (raising `ValidationError`) instead
of the typed domain error factories mandated by the Phase-1 Contract Completion
Design. This is a deliberate research simplification:

- The typed error factories (`from_payload()`, `from_json()`) are deferred to
  production implementation.
- Standard Pydantic `Field(min_length=1)` and `model_validator` checks provide
  sufficient validation for research runs.
- The `PersistenceSafetyError`, `BudgetExceededError`, and `WriteAuthorizationError`
  typed errors are still used where the plan explicitly requires them.

This simplification does NOT waive:
- Immutable nested state
- Exact full-ID aggregation
- Provenance-bearing score cells
- Explicit unavailable coverage states
```

### Revision 5: Add BudgetUsage Class Definition (Important)

Task 2 mentions `BudgetUsage` but doesn't show its definition:

> "Produces: `FeatureGates`, `BudgetLimits`, `BudgetUsage`, `EmbeddingConfig`, `ResolvedConfig`, and `resolve_profile()`."

The test shows:
```python
def test_budget_refuses_operation_above_limit() -> None:
    limits = BudgetLimits(max_rollouts=1)
    usage = BudgetUsage(rollouts=1)
    with pytest.raises(BudgetExceededError):
        usage.reserve(limits, rollouts=1)
```

But the `BudgetUsage` class definition is not provided. The architecture requires tracking:
- Agent rollouts
- Analyzer/judge calls
- Editor calls
- Validation calls
- Embedding calls
- Model tokens
- Attempts

**Resolution:** Add the `BudgetUsage` class definition to Task 2:

```python
@dataclass(slots=True)
class BudgetUsage:
    rollouts: int = 0
    analyzer_judge_calls: int = 0
    editor_calls: int = 0
    validation_calls: int = 0
    embedding_calls: int = 0
    model_tokens: int = 0
    attempts: int = 0
    accepted_edits: int = 0

    def reserve(self, limits: BudgetLimits, **kwargs: int) -> None:
        """Reserve budget for an operation. Raises BudgetExceededError if over limit."""
        for category, amount in kwargs.items():
            current = getattr(self, category, 0)
            limit = getattr(limits, f"max_{category}", None)
            if limit is not None and current + amount > limit:
                raise BudgetExceededError(f"{category} budget exceeded")
            setattr(self, category, current + amount)
```

## III. Important Observations (Non-Blocking)

### 1. The RHO Outer Stage Is Missing (But Task 12 Addresses It)

The plan covers the GEPA inner loop (pool, selection, editing, evaluation) but does not cover the RHO outer stage (coreset selection, proposal generation, initial pool seeding).

However, Task 12 provides a simplified B0/B1 harness that addresses this gap:

> "B0 keeps only its best initial candidate; B1 stores every initial candidate and derives a Pareto frontier from comparable fake-adapter evidence."

This is the correct approach for testing H1 without the full RHO pipeline. The plan should explicitly note that this is a simplified harness that will be replaced by the full RHO pipeline in a later phase.

**Recommendation:** Add a note to Task 12:

```markdown
Note: This smoke harness uses deterministic fake candidates instead of the full
RHO proposal pipeline. The full RHO outer stage (coreset selection, proposal
generation, initial pool seeding) will be implemented in a later phase. This
harness is sufficient for testing H1 (pool preservation vs. best-of-N discard)
with controlled inputs.
```

### 2. Entropy Refresh Modes Are Not Explicitly Implemented

The architecture defines three entropy refresh modes:
- `outer_iteration` (default)
- `accepted_edits`
- `pool_growth`

The plan mentions "Heap operations are deterministic and run only at a sequential barrier in this phase" but doesn't explicitly implement the refresh modes. Since Phase 1-4 is sequential only, `outer_iteration` is the only relevant mode.

**Recommendation:** Add the refresh mode to the config (already addressed in Revision 2) and note that only `outer_iteration` is active in Phase 1-4.

### 3. Verdict Sampler Is Not Mentioned

The architecture (Section 5.3) describes a task-local rollout diversity sampler for judge budget. The Phase 1-4 plan doesn't mention this. Since Phase 1-4 uses fake adapters, the verdict sampler may not be needed yet.

**Recommendation:** Add a note that the verdict sampler is deferred to a later phase.

### 4. Model Role Configuration Is Not Mentioned

The architecture (Section 5.1) defines three model roles: rollout agent, analyzer+judge, editor. The Phase 1-4 plan doesn't mention model role configuration. Since Phase 1-4 uses fake adapters, this may not be needed yet.

**Recommendation:** Add a note that model role configuration is deferred to a later phase.

### 5. Storage Simplification Should Be Explicitly Documented

The Phase 1-4 plan's storage implementation is much simpler than the Step-2 plan. It omits:
- SQLite WAL schema
- Atomic batch commits
- Idempotency
- Recovery
- Blob staging

This is consistent with the research simplification, but the plan should explicitly document what's being deferred.

**Recommendation:** Add a note to Task 3:

```markdown
Note: This JSON storage implementation is a research simplification. The
following production storage features are deferred to Phase 5:
- SQLite WAL schema with pragmas
- Atomic multi-record batch transactions
- Idempotency keys
- Recovery from interrupted transactions
- Content-addressed blob staging
- Orphan blob garbage collection
- Durable lease persistence

The JSON storage provides per-record temp-write-then-rename atomicity, which
is sufficient for single-threaded research runs.
```

### 6. Task 12 Metrics Should Be Fully Specified

Task 12 Step 6 says:

> "Expected: Three fixed-seed B0/B1 smoke records, with resolved configuration, redacted persistence, matched budgets, and no network/CUGA access."

But it doesn't explicitly list all the metrics to report. The Phase 1-4 Research Core Design says:

> "It reports held-out outcome mean and dispersion, pool size, comparison coverage, accepted/rejected attempts, and every budget category."

**Recommendation:** Add explicit metric reporting to Task 12:

```markdown
The smoke harness reports:
- Held-out outcome mean and dispersion (across 3 seeds)
- Pool size (B0 vs B1)
- Comparison coverage
- Accepted/rejected/no-op/exhausted attempt counts
- Every budget category (rollouts, analyzer/judge calls, editor calls,
  validation calls, embedding calls, model tokens, attempts)
- Resolved configuration manifest
```
