# Review: Phase 1–4 Research Simplification Design

## Overall Verdict

**Approve with four required revisions.** The design is architecturally sound, correctly prioritizes research-critical algorithms over production infrastructure, and maintains the binding contract boundaries. The approach selection is correct. However, there are four gaps that must be addressed before the specification is written.

---

## I. Approach Selection: Correct

The three approaches are well-framed and the rejection rationale is sound:

| Approach | Verdict | Reason |
|---|---|---|
| 1. Simplified persistence, full algorithms | ✅ **Approved** | Directly supports H1–H5 and B0–B4 without production database overhead |
| 2. Full production storage first | ❌ Rejected correctly | Delays B0–B4 without improving research claims |
| 3. In-memory only | ❌ Rejected correctly | Loses run provenance and auditability needed for paper reproducibility |

The key insight is right: **the research contribution is in the algorithms, not the storage engine.** JSON file persistence with atomic rename is sufficient for single-threaded research runs. The `StorageBackend` protocol preserves the upgrade path to SQLite WAL for production.

---

## II. Required Revisions

### Revision 1: Explicitly Document the Binding Architecture Deviation

The binding architecture (`docs/architecture/storage-and-transactions.md`) mandates SQLite WAL with specific pragmas. The design replaces this with JSON file storage. This is a legitimate research tradeoff, but the architecture enforcement design states:

> "docs/architecture/ is the binding implementation contract for AgentEvolve."

The design must explicitly acknowledge this deviation and frame it correctly. Add a section:

```markdown
## Research Simplification: Storage Backend

This Phase 1–4 design deliberately substitutes JSONFileStorage for the
binding SQLite WAL mandate in docs/architecture/storage-and-transactions.md.

Justification:
- Phases 1–4 are single-threaded research runs; WAL concurrency is unused.
- Research runs are short-lived and reproducible; crash recovery is unnecessary.
- The research contribution is in selection/editing algorithms, not storage durability.

Preserved from the binding mandate:
- Recursive fail-closed redaction gateway (mandatory, not simplified)
- Budget tracking with separate cost categories
- Manifest-safe profile and feature-gate serialization
- Opaque exact full-string IDs
- Atomic per-record writes (temp-write then rename)

Deferred to production upgrade:
- SQLite WAL with journal_mode=WAL, synchronous=FULL, foreign_keys=ON
- Content-addressed blob staging
- Multi-record atomic batch transactions with BEGIN IMMEDIATE
- Recovery from interrupted transactions
- Orphan blob garbage collection
- Durable lease persistence

This deviation is recorded in the architecture enforcement design as an
approved research simplification with a defined upgrade path. The
StorageBackend protocol ensures the upgrade is a backend swap, not a
redesign.
```

Without this, the next reviewer (or the agent itself) will flag the deviation as a binding violation.

### Revision 2: Add Internal Ordering to Phase 4

Phase 4 is the largest phase and contains five modules: `entropy.py`, `issues.py`, `memory.py`, `editor.py`, `evaluation.py`. The design lists them but does not specify implementation order within the phase.

The dependency chain within Phase 4 is:

```
entropy.py (statistics only, no selection)
    ↓
issues.py (consumes entropy, implements DPP, creates work items)
    ↓
memory.py (records attempt outcomes, provides RAG context)
    ↓
editor.py (consumes issues + memory, proposes edits)
    ↓
evaluation.py (validates edits, produces ValidationResult)
```

Specify this order explicitly. Each module should have its own TDD cycle with focused tests before the next module begins. This prevents the agent from trying to implement all five modules simultaneously.

### Revision 3: Add Generalization Probe Interface to evaluation.py

The design specifies evaluation.py as:

> "creates origin, worked-set, and regression validation plans"

This omits **generalization probes**, which are mandated by the architecture (Section 8.3):

> "Each proposed edit is first evaluated on: origin issue cases + worked-set regression cases + regression probes + 1-2 generalization probes"

Even if generalization probes are deferred to Phase 5 or 6 for full implementation, the `evaluation.py` interface must include them now. Otherwise, Phase 5 will require a breaking interface change.

Add to the evaluation.py scope:

```markdown
- Add evaluation.py:
  - creates origin, worked-set, regression, and generalization validation plans;
  - generalization probes are deferred by default (GEPA_GENERALIZATION_PROBE_MODE=deferred);
  - when deferred, evaluation records `generalization_unverified` rather than omitting the probe category;
  - produces ValidationResult with all four probe categories;
  - accepts only when primary gain and weighted net gain are positive and protected floors are satisfied;
  - records unavailable evidence rather than treating it as pass/fail.
```

### Revision 4: Specify Missing Configuration Defaults

The design mentions configuration but omits several architecture-mandated defaults that Phase 4 needs:

| Configuration | Architecture Default | Phase 4 Relevance |
|---|---|---|
| `GEPA_DPP_MAX_ITEMS` | 100 | Prefilter cap before dense kernel construction |
| `GEPA_ENTROPY_REFRESH_MODE` | `outer_iteration` | When entropy statistics are refreshed |
| `GEPA_ENTROPY_SCORE_FLOOR` | 0.15 | Floor for entropy multiplication |
| `GEPA_ENTROPY_RECOMBINATION_SCORE_THRESHOLD` | 0.30 | Two-tier entropy classification |
| `GEPA_ENTROPY_FRONTIER_WEIGHT` | 0.30 | Weight for frontier exploration items |
| `GEPA_CLUSTER_SIMILARITY_THRESHOLD` | 0.80 | Mechanism cluster assignment threshold |
| `GEPA_MAX_CLUSTERS_PER_TASK` | 12 | Maximum clusters per task |
| `GEPA_MECHANISM_EMBEDDING_MODEL` | `embeddinggemma` | Embedding provider for clustering |

For Phases 1–4 with the fake adapter, the embedding model will use lexical fallback. But the configuration values must still be resolved and recorded in the manifest. Add these to the Phase 2 config resolver scope.

## III. What Is Correct and Should Be Preserved

### Phase 1: Contract Consolidation ✅
- Retaining `contracts.py` and `errors.py` as the sole schema boundary is correct
- Migrating Phase 3–4 code to validated persisted record shapes prevents a third model layer
- Maintaining exact full-ID aggregation, provenance-bearing score cells, and adapter neutrality is essential
- Continuing with `fake_adapter.py` is correct for Phases 1–4

### Phase 2: Research Persistence ✅
- Four named profiles with immutable `ResolvedConfig` is correct
- `StorageBackend` protocol with `JSONFileStorage` is the right simplification
- Path validation preventing writes outside the storage root is a necessary safety measure
- Centralized recursive redaction gateway is correctly preserved (this is a safety requirement, not a production luxury)
- Budget tracking persisted as records is correct
- Documenting deferred production work explicitly is correct

### Phase 3: Evidence, Diagnosis, and Pool ✅
- Splitting into `analysis.py`, `blame.py`, `clustering.py`, `pool.py` matches the architecture's planned code boundaries
- Score comparisons using validated `ScoreCell` with comparability predicates is correct
- Pareto using severity-and-confidence weighted scores with unavailable exclusion is correct
- Testing against deterministic fake adapter with incomplete evidence and full-ID collision cases is thorough

### Phase 4: Selection and Editing ✅
- Narrowing `entropy.py` to incremental statistics only is correct
- `issues.py` with full hierarchical DPP, greedy MAP Schur updates, and all ablation modes is the research-critical work
- `memory.py` with append-only redacted records and scoped retry exhaustion is correct
- `editor.py` narrowed to protocol and authorization boundary is correct
- `evaluation.py` with focused validation and protected floor enforcement is correct

### Compatibility Strategy ✅
- Not widening the prototype orchestrator is correct
- Replacing prototype-only tests with target-contract tests is correct
- Keeping `FakeAdapter` deterministic and as the only runtime is correct

### Verification Strategy ✅
- Tests written first, module by module, is correct
- `2>&1 | tee` for all commands is correct
- First experiment target of B0 vs B1 with persisted configs is correct and tests H1

## IV. Observations (Not Blocking, But Worth Noting)

### 1. The DPP Prefilter Should Be Explicitly Bounded
The design mentions "documented prefiltering" but should explicitly state: "Prefilter to at most `GEPA_DPP_MAX_ITEMS` (default 100) items using the entropy heap and quality ranking before constructing the dense kernel. Record the prefilter threshold and item counts in the selection report."

### 2. The Compatibility Strategy Should Name Specific Prototype Flaws Being Replaced
The design says "replace tests that encode prototype-only behavior with target-contract tests." This is correct but vague. The known prototype flaws from `f1.md` should be explicitly listed as behaviors being replaced:

- `mean_score_per_task()` using `_[0]` → replaced with full task ID aggregation
- `floors_violated()` containing `pass` → replaced with mechanism-cluster-aware floor checking
- DPP rewarding similarity → replaced with greedy MAP Schur complement DPP
- Shallow sanitization → replaced with recursive redaction gateway
- Orchestrator applying edits without write-set enforcement → replaced with adapter-level authorization

### 3. The Design Should State That Parallel Execution Is Not Tested in Phases 1–4
The `research_parallel` profile exists in the config resolver, but Phases 1–4 do not implement parallel execution. The design should state: "The `research_parallel` profile is resolved and validated in Phase 2 configuration, but parallel execution is not implemented or tested until Phase 5. The `parallel_execution` feature gate is resolved but inactive."

### 4. Budget Tracking Should Include Embedding Calls
The architecture's budget reporting (Section 3.2 of the research hypotheses) requires reporting "embedding calls" separately. The design mentions "rollout, analysis, editor, validation, and attempt consumption" but not embedding calls. Add embedding call tracking to the budget object.

### 5. The First Experiment Should Specify Seed and Repetition Count
The design says "fixed-budget B0 versus B1" but doesn't specify:
- Number of seeds (the research hypotheses say "no causal claim should rest on one smoke run")
- Budget level (matched rollout budgets)
- Task set (fixed coreset from historical corpus)

Add: "Run B0 vs B1 with at least 3 seeds, matched rollout budgets, and the fixed DPP coreset. Report mean and dispersion of held-out outcome."
